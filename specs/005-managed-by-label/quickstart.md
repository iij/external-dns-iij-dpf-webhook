# Quickstart: 動作確認の手順

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-16

本書は、実装が spec の受け入れ条件を満たすことを確認する手順をまとめる。
実装コードは含まない。詳細は [contracts/](./contracts/) と
[data-model.md](./data-model.md) を参照。

---

## 前提

| 項目 | 内容 |
|---|---|
| Go | 1.27 以降 |
| DPF | 破壊的操作を行ってよい**検証用ゾーン**と、そのゾーンを操作できるアクセストークン |

**警告**: 本書の手順は DNS レコードを実際に変更する。本番ゾーンでは実行しない。

001 の検証用ゾーンをそのまま使える。本機能のために新しいゾーンは要らない。

## 1. 投入集合のラベルが印のみになること (単体)

DPF へ到達せずに確かめられる範囲。

| 確認 | 期待される結果 |
|---|---|
| 作成するレコード | ラベルが `managed-by: external-dns-iij-dpf-webhook` のみ (FR-001) |
| 更新するレコード | 同上。印が無かったものにも付く |
| `TXT` を含む変更セット | `TXT` のラベルも印のみ (FR-002) |
| ExternalDNS の所有権 `TXT` を模した変更セット | 印が付く。**特別な扱いを要しない** (SC-002) |
| **変更セットに含まれないレコード** | **ラベルが変わらない** (FR-003) |
| 独自のラベルを持つレコードを更新 | **ラベルは印のみになる。独自のラベルは失われる** (PC-001) |
| `managed-by` に別の値があるレコードを更新 | 自身の名前になる |
| 既に印が付いたレコードを更新 | ラベルが変わらない (FR-005) |
| 反映済みレコードのラベルのマップ | **書き換えられていない** (research R3) |

**「独自のラベルが失われる」を表明として書く。** これは仕様であり、不具合ではない
(PC-001)。表明しておかないと、後から「保持すべきだ」と直されて上限の扱いが
必要になる。

**上限 (10 件) の確認項目は無い。** ラベルは常に 1 件であり、触れる経路が存在しない
(research R2)。

## 2. 印が DPF 上に付くこと (実環境)

要求に載せることと、DPF が保存することは別である。

```bash
DPF_E2E_TOKEN_FILE=<token> DPF_E2E_ZONE=<zone> go test ./test/e2e/... -run TestManagedByLabel -v -count=1
```

| 確認 | 期待される結果 |
|---|---|
| レコードを作成して読み戻す | ラベルが印のみである (FR-001、SC-001) |
| 所有権 `TXT` を含む適用の後に読み戻す | `TXT` にも印が付いている (SC-002)。`e2e-sidecar` でも確認できる |
| 印で絞り込んで一覧を取る | 当該レコードが含まれる (FR-006) |
| 印で絞り込んだ一覧 | **管理外のレコードが 1 件も含まれない** (SC-003) |
| 印の付与を理由に失敗する適用 | **0 件** (SC-005) |
| ラベルの値の長さ | DPF に拒否されない (28 文字 < 63) |
| 適用を 2 回繰り返す | ラベルの状態が変わらない (FR-005) |

## 3. 人手のレコードが巻き込まれないこと (実環境・一部手作業)

| 手順 | 期待される結果 |
|---|---|
| DPF コンソールから人手でレコードを作る | 印は付かない |
| 本 provider から**別の**レコードを適用する | 人手のレコードの内容もラベルも変わらない (FR-003、SC-004) |
| 印で絞り込む | 人手のレコードは含まれない (SC-003) |

**DPF コンソールでの作成は機械化しない。** 機械化しない理由を実装時にテストの
冒頭へ記す (001・004 の quickstart と同じ方式)。

なお、**本 provider が触らないレコードのラベルが変わらないこと** (FR-003、SC-004) は
機械化する。人手のレコードを巻き込まないことが、印の価値の前提である。

---

## 4. 既存の振る舞いを壊していないこと

本機能は 001 の適用経路に乗る。**壊していないことの確認が、付けたことの確認と
同じだけ重要である。**

| 確認 | 期待される結果 |
|---|---|
| 同一の変更セットを繰り返し適用する | DNS の最終状態が変わらない (001 FR-010、SC-006) |
| 管理対象外のレコード | 変更・削除されない (001 FR-009) |
| `SOA`・ゾーン apex の `NS` | 逐語的に保たれ、印も付かない |
| レコードのコメント | 逐語的に保たれる |
| 触らないレコードのラベル | 逐語的に保たれる (FR-003) |
| ゾーン反映の説明 | 004 の記録が付き続ける |
| `GET /records` の応答 | **ラベルが現れない** (FR-004) |
| ExternalDNS との往復 | 差分が振動しない (001 SC-007) |

既存の e2e (`TestLifecycle`、`TestUnmanagedRecordsUntouched`、`TestApplyAttribution`、
`TestScale`) と `e2e-sidecar` がそのまま通ることをもって確認する。

**`e2e-sidecar` を省かない。** 001 の SC-007 (差分の振動) は、単体テストでは
現れない。004 の実装後に 3 度の実行を要して原因を突き止めた経緯がある。
