# Phase 0 Research: レコードに管理者の印を付ける

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-16

調査対象は `github.com/iij/dpf-go` v0.1.0 の同梱 OpenAPI 定義 (`openapi.json`)、
生成型、および DPF のマニュアルである。

---

## R1. ラベルの制約

**Decision**: 上限は **1 レコードにつき 10 件**。値は 1〜63 文字。名前と値に使えるのは
英数字と `.`、`-`、`_`。

典拠は 2 つある。

`openapi.json` の共通スキーマ `RecordLabels`:

```json
{
  "type": "object", "default": {},
  "minProperties": 0, "maxProperties": 10,
  "additionalProperties": { "type": "string", "minLength": 1, "maxLength": 63 }
}
```

文字種は DPF のマニュアル「ラベルの共通ルール」
(<https://manual.iij.jp/dpf/help/50639516.html>) にある。**スキーマは文字種を
宣言していないため、マニュアルが唯一の典拠である。**

| 項目 | 値 |
|---|---|
| 個数の上限 | 10 |
| 値の長さ | 1〜63 文字 |
| 名前・値の文字種 | 英数字と `.` `-` `_` |
| 予約された名前 | 記載なし |

`managed-by` / `external-dns-iij-dpf-webhook` はいずれもこの範囲に収まる
(28 文字、ハイフンのみ)。

**004 の教訓を適用した**: 004 では「生成された Go の型が長さ検証を持たないこと」を
「スキーマに宣言がないこと」と混同し、確認できる事実を未確認として扱った。
今回は先に `openapi.json` とマニュアルの双方を読んだ。

---

## R2. 毎回上書きする。上限の扱いは要らなくなる

**Decision**: 本 provider が書くレコードのラベルを、**毎回、印のみからなる状態に
設定する。** 既存のラベルは保持しない。

**Rationale**: 制約が 2 つ構造的に消える。

| 消えるもの | 理由 |
|---|---|
| ラベル 10 件の上限 | 常に 1 件になる。**上限に触れる経路が存在しない** |
| ラベルのマップの共有 | マップごと差し替えるため、読み取った側を書き換えない |

2 つ目は R3 で述べる問題である。`toOverwrite` は反映済みレコードのラベルのマップへの
**参照**を投入集合へ入れる。加算方式なら写しを作る必要があったが、**差し替えなら
元のマップに触れない。**

上限の扱いを定めなくてよいことが大きい。加算方式では「上限に達したら印を付けずに
続行する」という分岐が必要で、そこには「一括更新はゾーン単位なので、拒否されると
ゾーン全体の適用が失敗する」という判断が伴った。**設定しない分岐は壊れない。**

**代償**: 運用者が本 provider のレコードに付けたラベルは、次の更新で失われる。
これは spec の利用前提条件 PC-001 として明示した。

**Alternatives considered**:

- *既存のラベルを保持して印を加える*: 却下。上限の扱いと写しの手当てが必要になる。
  守るべきものは「運用者が本 provider のレコードに付けたラベル」だが、**そこに
  情報を持たせることは元から保証されていない。** 001 の利用前提条件が述べるとおり、
  値そのものも ExternalDNS が書き戻す
- *印以外のラベルがある場合だけ保持する*: 却下。条件分岐が増え、どちらの経路を
  通ったかで結果が変わる。**毎回同じ状態に収束するほうが、振る舞いを説明しやすい**

**保証しない範囲を数え上げない**: 印の付いたレコードを外から変更する経路は
列挙しきれない。ラベルを消すこともできるし、ExternalDNS の所有権 `TXT` を手で
削除することもできる。PC-001 は「保証しない」ことだけを述べ、個々の帰結を
並べることはしない。

**初版からの変更 (2026-09-16)**: 初版は加算方式を前提とし、上限に達した場合の扱い
(FR-006) を重要な要件として扱っていた。**上書き方式ではその要件自体が不要になる。**
spec から FR-006 と、既存ラベルの保持を求める US2・FR-004 を削除した。

## R3. 印を付ける場所

**Decision**: マージ結果に対して、変更セットの対象だけに印を付ける。

001 のマージは 3 段で構成される (`internal/dpf/merge.go`)。

| 段 | 内容 | 印 |
|---|---|---|
| 1. 反映済みの内容を土台にする | 逐語コピー (`toOverwrite`) | 付けない |
| 2. 削除対象を落とす | — | 対象外 |
| 3. 作成と更新を反映する | 変更後の内容を投入 | **ここに該当** |

段 3 の対象がちょうど FR-001〜FR-003 の対象である。

- 作成したレコード → 付く
- 更新したレコード → 付く
- **ExternalDNS の所有権 `TXT`** → 変更セットに通常のレコードとして入るため、
  特別な扱いなしに付く (FR-003)
- 触らないレコード → 段 1 のまま。付かない (FR-003)
- `SOA`・ゾーン apex の `NS` → 変更セットに入らない。付かない

**Alternatives considered**:

- *`merge` の内部に印の付与を織り込む*: 却下。`merge` は投入集合の組み立てという
  一つの責務を持ち、テストもそれを見ている。印の判断 (上限、既存の値) を混ぜると、
  どちらの誤りで落ちたのか読みにくくなる。**マージ結果に対する独立した段**とし、
  単体で検証できるようにする
- *レコードを投入する直前に全件へ付ける*: 却下。触らないレコードにも付いてしまう
  (FR-003 違反)

### マップを差し替えるため、共有の問題が起きない

`toOverwrite` は `r.GetLabels()` の戻り値を**そのまま**投入集合へ入れる。これは
反映済みレコードが持つマップへの参照である。加算方式ならここを書き換えることになり、
`current` 側のマップも変わってしまう。

**上書き方式では新しいマップを代入するため、元のマップに触れない** (R2)。
写しを作る手当ても要らない。

なお `toOverwrite` が参照を共有していること自体は残る。現在の実装では投入前ガードが
名前と種別だけを見るため害は出ていないが、**`current` のラベルを後から参照する処理を
足すときは注意が要る。** 本機能はその経路を作らない。

## R4. 絞り込みの手段

**Decision**: DPF のレコード一覧はラベルで絞り込める。検証にのみ用いる読み取りを
境界の内側に用意する。

`GET /zones/{ZoneId}/records/currents` の問い合わせパラメータに `KeywordsLabel` が
ある。生成された Go では次の形である。

```go
func (r ApiGetRecordCurrentsRequest) KeywordsLabel(keywordsLabel []string) ApiGetRecordCurrentsRequest
```

指定の形は `openapi.json` の `KeywordsLabel` に「Value は『label の Key=label の
Value』のようにイコール区切りで指定」とある。

**FR-006 は DPF の機能で満たされる。** 本 provider が絞り込みの手段を提供するのでは
なく、印を付けることで DPF の絞り込みが使えるようになる。

**検証のために読み取りを実装する**: SC-003 (印で絞ったとき管理外のレコードが
含まれない) を機械的に確かめるには、絞り込んだ一覧を取得する必要がある。004 の
ゾーン反映履歴と同じ扱いとする。**通常の動作経路では使わない。**

## R5. ExternalDNS への影響

**Decision**: 影響しない。実装上の手当ても要らない。

ドメインの型 `provider.Record` は名前・種別・TTL・値だけを持ち、ラベルを持たない。
DPF から読み取る変換 (`toProviderRecord`) もラベルを写さない。したがって印が
ExternalDNS へ渡る経路が存在しない (FR-004)。

**004 の轍を踏まない**: 004 では調整の応答が上流のフィールドを落としており、
ExternalDNS 自身の状態を壊していた。今回は逆方向 (DPF 側の情報を上流へ出さない) で
あり、出さないことが要件である。**ラベルを転送形へ足してはならない。**

差分の振動 (SC-006、001 の SC-007) も起きない。印は DNS のデータではなく、
ExternalDNS が比較する 4 つの条件 (TTL、値、provider 固有の属性、旧所有者) の
いずれにも現れない。

## R6. 印の名前と値

**Decision**: 名前は `managed-by`、値は `external-dns-iij-dpf-webhook`。
**値は 004 と同じ定数を使う。**

004 はゾーン反映の説明に `external-dns-iij-dpf-webhook` を記録している
(`applyAttribution`)。同じものを指す印が 2 つの表記を持つと、片方だけ直した変更で
食い違う。**定数を 1 つに保つ。**

**名前に前置きを付けない**: DPF のマニュアルは名前に「prefix」を許すとし、その形は
「DNS のドメイン名と同じ形式」とある。しかし文字種の規則 (英数字と `.` `-` `_`) は
区切りの `/` を含まず、**前置き付きの名前が実際に通るかは読み取れない。**

利用者が指定した `managed-by` をそのまま採る。前置きのない一般的な名前であるため、
他の仕組みが同じ名前を別の意味で使う余地がある。その場合は値が置き換わる (FR-005)。
これは同一レコードを複数の仕組みが書いている状態であり、001 の利用前提条件 PC-001 が
扱う範囲の問題である。

---

## R7. 掃除を範囲に含めない

**Decision**: 印を付けるところまでを本機能とする。掃除は別に扱う。

本機能の動機は、検証用ゾーンに溜まった過去の検証のレコードを安全に消すことだった。
しかし印付けと掃除は独立して価値と危険を持つ。

- 印付けは**加える**操作である。既存の状態を壊さない (US2)
- 掃除は**消す**操作である。対象を誤れば復旧に TTL の分だけかかる

**遡って印を付けることもしない**: 全件を書き換えれば既存のレコードにも印が付くが、
ゾーン全体を書き換える操作は得るものに対して危険が大きい。既存のレコードは次に
更新されたときに印が付く。

**したがって、今ある残留レコードは印では見つからない。** 既存分を消すには別の手段が
要る。本機能はそれを提供しない。

**未調査として残っていること**: 検証の後始末 (`残留レコードを消す` と
`TestSidecarForceDelete`) が ✓ を返しているにもかかわらず、前回の実行のレコードが
残っていた。**後始末が動いていない理由は分かっていない。** 掃除の仕組みを作る前に
ここを見る必要がある。印があっても、消す処理が動いていなければ残る。
