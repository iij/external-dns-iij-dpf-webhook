# Feature Specification: レコードに管理者の印を付ける

**Feature Branch**: `feature/create-webook`

**Created**: 2026-09-16

**Status**: Draft

**Input**: User description: "recordsのlabelをつかって、external-dnsで管理されていることを表明します。managed-by: external-dns-iij-dpf-webhookを付与してください。これはtxtでのmetadataのレコードも含みます。" / 追加の指示: "AtomicUpdateで毎回上書きしましょう。managed-byラベルが付いているレコードはそのアプリケーション以外からの変更は可能ですが、動作は保証できません。"

## User Scenarios & Testing *(mandatory)*

本機能の利用者は **DPF のゾーンを運用する人** である。本 provider が管理するゾーンには、
本 provider が書いたレコードと、人手や他の仕組みが書いたレコードが混在する。
現状、**レコードを見ても、どちらが書いたものか分からない。**

### User Story 1 - 管理下のレコードを見分ける (Priority: P1)

ゾーンの運用者が DPF 上のレコードを見たとき、本 provider が管理しているものには
印が付いている。印で絞り込めば、管理下のレコードだけを一覧できる。人手で作った
レコードと混同して消してしまう事故が起きない。

**Why this priority**: これが本機能の価値のすべてである。**印がなければ、掃除や
棚卸しの対象を安全に決められない。** 名前の規則で当てるしかなく、規則から外れた
ものを巻き込む。

**Independent Test**: 検証用ゾーンに対して本 provider からレコードを作成し、DPF 上で
そのレコードのラベルが印のみであることを確認する。続いて人手でレコードを作り、
そちらには印が付かないことを確認する。印で絞り込んで、前者だけが返ることを確認する。

**Acceptance Scenarios**:

1. **Given** 本 provider が管理するゾーンがある、**When** 本 provider がレコードを
   作成する、**Then** そのレコードのラベルは
   `managed-by: external-dns-iij-dpf-webhook` **のみ**である
2. **Given** 印の付いていない既存のレコードを本 provider が更新する、**When** 適用
   される、**Then** ラベルは印のみになる
3. **Given** ExternalDNS が所有権の記録として `TXT` レコードを書く、**When** それが
   適用される、**Then** **その `TXT` のラベルも印のみ**である
4. **Given** 人手で作成したレコードがある、**When** 本 provider が別のレコードを
   適用する、**Then** 人手のレコードのラベルも内容も変わらない
5. **Given** 印の付いたレコードと付いていないレコードが混在する、**When** 運用者が
   印で絞り込む、**Then** 本 provider が管理するレコードだけが返る
6. **Given** 既に印の付いたレコードがある、**When** 同じ内容を再度適用する、**Then**
   ラベルも内容も変わらない

---

### Edge Cases

- 本 provider が触らないレコードには印が付かない。ラベルも内容も変わらない
- `SOA` およびゾーン apex の `NS` には印が付かない。これらは本 provider が
  管理対象としないレコードであり、逐語的に保たれる
- 印は DPF 側にのみ存在し、ExternalDNS へ返すレコードには現れない。ExternalDNS の
  差分計算に影響しない
- 本機能より前に本 provider が書いたレコードには印が付いていない。次にそのレコードを
  更新したときに付く。**遡って付けることはしない**
- 印の付与によって DNS の名前解決は変わらない
- **ラベルは常に印 1 つだけになるため、DPF の上限 (1 レコードにつき 10 件) に
  触れることがない**
- 運用者が本 provider のレコードに独自のラベルを付けていた場合、次の更新で失われる
  (PC-001)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、自身が作成・更新するレコードのラベルを、
  `managed-by: external-dns-iij-dpf-webhook` **のみからなる状態に設定**しなければ
  ならない。既存のラベルは保持しない
- **FR-002**: システムは、ExternalDNS が所有権の記録として書く `TXT` レコードにも
  同じ設定をしなければならない。**これらも本 provider が書くレコードである**
- **FR-003**: システムは、自身が触らないレコードのラベルを変更してはならない
- **FR-004**: システムは、印を ExternalDNS へ返すレコードに含めてはならない。
  印は DPF 側の情報であり、ExternalDNS の差分計算に影響してはならない
- **FR-005**: システムは、同一の内容を再度適用しても、ラベルの状態を変えては
  ならない。設定は冪等でなければならない
- **FR-006**: システムは、印によってレコードを絞り込めるようにしなければならない。
  運用者が管理下のレコードだけを一覧できる必要がある

### Key Entities

- **管理者の印 (Managed-By Label)**: レコードに付ける名前と値の対。名前は
  `managed-by`、値は `external-dns-iij-dpf-webhook`。**DNS のデータではない。**
  名前解決に影響せず、ExternalDNS へも渡らない
- **レコードのラベル**: 1 つのレコードに付けられる名前と値の対の集まり。本 provider が
  書くレコードでは、**常に印 1 つだけ**になる

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 本 provider が作成・更新したレコードのうち、ラベルが印のみでないものが
  0 件である
- **SC-002**: ExternalDNS が書く所有権の `TXT` レコードのうち、印が付かないものが
  0 件である
- **SC-003**: 運用者が印で絞り込んだとき、本 provider が管理していないレコードが
  1 件も含まれない
- **SC-004**: 本 provider が触らないレコードのラベルが変更される件数が 0 件である
- **SC-005**: 印の付与の前後で、同一の変更セットを適用したときの DNS の最終状態が
  変わらない
- **SC-006**: 印の付与を理由に失敗する適用が 0 件である

## 利用前提条件

- **PC-001**: 印の付いたレコードは本 provider が管理する。**他の手段から変更する
  ことは可能だが、動作は保証しない。** ラベルは次の更新で印のみに戻り、値は
  ExternalDNS があるべき状態へ書き戻す。

  これは 001 の利用前提条件 (PC-001〜PC-004) が述べる性質を、レコード単位で
  言い直したものである。**保証しない範囲を数え上げることはしない。** 手で所有権の
  `TXT` を消すこともできるように、外から触れる経路は列挙しきれない。

## Assumptions

- DPF はレコードに名前と値の対をラベルとして付けられ、それで絞り込んだ一覧を
  取得できる
- 名前と値に使えるのは英数字と `.`、`-`、`_` であり、値の長さは 63 文字までである。
  `managed-by: external-dns-iij-dpf-webhook` はこの範囲に収まる
- **ラベルを毎回上書きするため、上限 (1 レコードにつき 10 件) に触れる経路が存在
  しない。** 上限に達した場合の扱いを定める必要がない
- 印の名前を `managed-by` とする。前置きのない一般的な名前であり、他の仕組みが
  同じ名前を別の意味で使っていた場合、その値は失われる。これは PC-001 が述べる
  範囲の帰結である
- 値は 004 でゾーン反映の記録に使う名前と同じ `external-dns-iij-dpf-webhook` とする。
  同じものを指す印が 2 つの表記を持たないようにする
- **印を使った掃除そのものは本機能の範囲外とする。** 本機能は絞り込める状態を
  作るところまでを担う。何をいつ消すかは運用の判断であり、別途定める
- 本機能より前に書かれたレコードを遡って印付けすることはしない。全件を書き換える
  操作は、得るものに対して危険が大きい

## Dependencies

- **001 の適用経路**: 印はレコードを投入する経路に乗る。001 が確立した
  「管理対象外のレコードは逐語的にコピーする」規則を崩さないことが前提となる
- **DPF のレコードのラベル**: 印の保存先。ラベルの設定と、ラベルによる絞り込みの
  双方を DPF が提供することが前提となる
- **検証用の DPF ゾーン**: 受け入れ確認には、破壊的操作を行ってよい検証用ゾーンが
  必要である

## 背景: なぜ必要か

001 の利用前提条件 (PC-001〜PC-004) は、本 provider が管理するゾーンを他者と
共有する場合の制約を定めている。004 はゾーン反映の履歴に実行者を記録し、
「**いつ誰が変更したか**」を追えるようにした。

本機能が埋めるのは別の穴である。**「このレコードは誰のものか」**が分からない。
履歴は操作の記録であり、レコードそのものには何も書かれていない。

これが実際に問題になったのは、検証用ゾーンに過去の検証が残したレコードが溜まった
ときである。消したいが、名前の規則で当てるしかなく、規則から外れたものや人手で
作ったものを巻き込む危険があった。**印があれば、対象を「本 provider が書いたもの」に
限れる。**

なお印は事故を減らすが、なくすわけではない。印が付いていても、そのレコードが
今も必要かどうかは別の判断である。
