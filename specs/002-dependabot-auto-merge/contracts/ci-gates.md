# Contract: 更新 Pull Request に対する検査の振る舞い

**Feature**: [../spec.md](../spec.md) | **Date**: 2026-09-09

更新 Pull Request に対して既存の CI が満たすべき契約。

**新しい検査経路を作らない。** 依存更新のために検査を減らした経路を設けない
ことが FR-010 の要件である。既存の `ci.yml` / `e2e.yml` / `e2e-sidecar.yml` が
そのまま担う。

---

## 起点によって使える秘密情報が変わる

これは GitHub の仕様であり、本機能の設計で変えられない。

| 起点 | `GITHUB_TOKEN` | Actions secrets | Dependabot secrets |
|---|---|---|---|
| `dependabot[bot]` | 読み取り専用 | **参照できない** | 参照できる |
| 保守担当者 | 通常 | 参照できる | — |

したがって、同じワークフローが同じ Pull Request に対して 2 通りの結果を出す。
これを異常ではなく**設計として扱う**。

---

## 満たすべき振る舞い

### 秘密情報を要する検査 (FR-014)

- Dependabot 起点の実行では**失敗すること (MUST)**。
- 秘密情報が無いことを理由に**飛ばさないこと (MUST NOT)。** GitHub の分岐
  (`if:`) で飛ばした検査は「skipped」となり、ブランチ保護では成功として
  数えられる。検査を経ずにマージできる状態が生まれる (SC-004)。
- 失敗の理由に、**次に何をすべきかを含めること (MUST)**。「秘密情報が無い」
  だけでは、更新によって壊れたのか設定が足りないのかが分からない (FR-019)。

失敗時に伝えるべき内容:

```
この Pull Request は Dependabot が起点であるため、Actions secrets を参照できません。
更新内容 (上流の差分) を確認したうえで、この Pull Request のブランチへ
コミットを 1 つ積んでください。以降の実行では全検査が実行されます。
```

### 秘密情報を要しない検査 (FR-012)

- Dependabot 起点の実行でも**実行されること (MUST)**。
- 対象: シークレットの混入検査、整形、SPDX ヘッダ、ワークフローの静的検査、
  設定の不変条件。

### 実際の DPF に対する検証 (FR-016)

- 並列に実行しないこと (MUST NOT)。既存の `concurrency` グループ
  `e2e-verification-zone` をそのまま使う。
- 複数の更新 Pull Request があるとき、後続は待つこと (MUST)。

### 検証済みへの移行 (FR-015)

- 保守担当者がブランチへコミットを積んだ後の実行で、**必須検査すべてが
  実行され、その結果が Pull Request に紐づくこと (MUST)**。
- この経路のために新しいワークフローを作らないこと (MUST NOT)。通常の
  `pull_request` の実行がそのまま該当する。

### マージ (FR-009、FR-010)

- 自動でマージしないこと (MUST NOT)。
- 必須検査すべての成功と、レビュー承認をマージの条件とすること (MUST)。
- 依存更新のために必須検査の集合を変えないこと (MUST NOT)。

---

## 定期検査が満たすべき振る舞い

`scheduled.yml` に足す検査。起点が定期実行であるため Actions secrets が使える。

### 提案の欠落 (FR-017、SC-009)

- `go list -m -u all` が示す更新可能な直接依存と、開いている Dependabot の
  Pull Request が含む依存を照合すること (MUST)。
- 期待側にあって実際側にないものが**待機期間 (5 日) を超えて**存在する場合、
  報告すること (MUST)。
- 待機期間内の版を「提案されていない」と報告しないこと (MUST NOT)。5 日以内に
  公開された版は提案されないのが正しい。

### 滞留 (FR-018、SC-008)

- 開いている Dependabot の Pull Request のうち、作成から **30 日**を超えた
  ものを報告すること (MUST)。
- 自動で閉じないこと (MUST NOT)。FR-011 が禁じる。

### 報告先

- 既存の `notify` ジョブと同じ経路 (Issue) を使うこと (MUST)。
- 新しい通知手段を足さないこと (MUST NOT)。

---

## この契約が隠すもの

更新 Pull Request を扱う保守担当者から見た手順は 3 つに収まる。

1. 上流の差分を確認する (Dependabot が Pull Request に載せる比較を見る)
2. ブランチへコミットを 1 つ積む
3. 全検査が緑になったらレビュー承認してマージする

秘密情報の参照可否が起点で変わるという事情は、失敗メッセージが手順 2 を
案内することで吸収される。保守担当者が GitHub の仕様を知る必要はない。
