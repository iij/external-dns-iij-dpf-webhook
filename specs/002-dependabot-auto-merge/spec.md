# Feature Specification: 依存パッケージの更新 Pull Request の自動作成

**Feature Branch**: `002-dependabot-auto-merge`

**Created**: 2026-09-09

**Status**: Draft

**Input**: User description: "依存パッケージの自動アップデートのため dependabot による自動 PR 作成をします。ただし、pkg 汚染を考慮して、cooldown は 5 日間とします。PR 作成後 CI が通ればそのままマージされます。" — 後に「CI が通ればそのままマージは修正します。PR を作成するまでにします」として自動マージを範囲から除外。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 依存の更新が自動で提案される (Priority: P1)

保守担当者は、依存パッケージに新しい版が出たことを自分で調べなくてよい。
新しい版が公開されてから一定期間が経つと、その更新を適用する Pull Request が
自動で作られる。

**Why this priority**: これが本機能の中心である。「更新に気付く」「更新差分を
用意する」という手作業がなくなる。以降のストーリーはこの上に載る。

**Independent Test**: 依存に更新可能な版があり、その公開から待機期間が過ぎている
状態で、更新 Pull Request が作られることを確認する。

**Acceptance Scenarios**:

1. **Given** 依存パッケージの新しい版が 5 日以上前に公開されている、**When** 定期実行の時刻が来る、**Then** その版へ更新する Pull Request が作られる
2. **Given** 依存パッケージの新しい版が 5 日以内に公開された、**When** 定期実行の時刻が来る、**Then** その版への更新 Pull Request は作られない
3. **Given** 複数の依存に更新可能な版がある、**When** 更新 Pull Request が作られる、**Then** 同じ種別の依存はまとめられ、Pull Request の数が依存の数に比例して増えない
4. **Given** 依存に既知の脆弱性が公開された、**When** 修正版が公開される、**Then** **待機期間を待たずに**更新 Pull Request が作られる
5. **Given** 互換性のない変更を含む版 (メジャー版) への更新がある、**When** 待機期間が過ぎている、**Then** その更新も Pull Request として提案される。提案の対象から除外しない

---

### User Story 2 - 更新の可否をレビュー時点で判断できる (Priority: P2)

保守担当者は、更新 Pull Request を見た時点で、その更新を取り込んでよいかを
判断できる。何が変わるのか、既存の品質ゲートを通るのかが揃っている。

**Why this priority**: US1 だけでは「更新の候補が並ぶ」に留まる。取り込みの
判断に必要な材料が揃っていなければ、結局差分を手元に持ってきて確かめる作業が
残る。マージは人が行うため、判断材料の質がそのまま保守の手間を決める。

**Independent Test**: 更新 Pull Request に対して品質ゲートが実行され、その結果が
Pull Request 上で確認できることを検証する。

**Acceptance Scenarios**:

1. **Given** 更新 Pull Request が作られた、**When** 保守担当者が Pull Request を開く、**Then** 更新前後の版と変更内容の所在が本文から分かる
2. **Given** 更新 Pull Request が作られた、**When** 品質ゲートが実行される、**Then** 各検査の成否が Pull Request 上で確認できる
3. **Given** 秘密情報を必要とする検査が更新 Pull Request の文脈で実行できない、**When** 検査が処理される、**Then** その検査は「未実行」または「失敗」として現れる。成功として現れない
4. **Given** 保守担当者が更新内容を確認して承認した、**When** マージする、**Then** 憲章が必須とする検査すべてが成功していることがマージの条件になっている

---

### User Story 3 - 提案が滞留していることに気付ける (Priority: P3)

保守担当者は、取り込まれずに残っている更新の提案があることに気付ける。

**Why this priority**: US1 と US2 が動けば、更新の提案と判断材料は揃う。
しかしマージが人の操作であるため、Pull Request が開いたまま忘れられる状態が
必ず生まれる。放置された脆弱性の修正は、自動化していない場合より危険である
(「自動化してあるから大丈夫」と思われるため)。

**Independent Test**: 一定期間マージされていない更新 Pull Request がある状態で、
その存在が保守担当者に伝わることを確認する。

**Acceptance Scenarios**:

1. **Given** 更新 Pull Request が作られてから一定期間マージされていない、**When** 定期実行の時刻が来る、**Then** 滞留している提案があることが保守担当者に伝わる
2. **Given** 更新 Pull Request の品質ゲートが失敗している、**When** 保守担当者が Pull Request を見る、**Then** どの検査が失敗したかが分かる
3. **Given** 更新 Pull Request が他の変更と競合してマージできない、**When** 競合が発生する、**Then** 競合していることが分かる

---

### Edge Cases

- **公開直後に取り下げられた版**: 版が公開されてから待機期間内に取り下げ (yank) や
  差し替えが行われた場合、その版への更新 Pull Request は作られない。待機期間を
  設ける目的がこれである。
- **待機期間中に更新が積み上がる**: 待機期間の間に同じ依存の版がさらに進んだ場合、
  待機期間を満たした最新の版へ 1 度で更新する。中間の版を経由しない。
- **複数の更新 Pull Request が同時に走る**: 実際の DPF に対する検証は検証用ゾーンを
  共有するため並列に実行できない (憲章「実環境での検証」)。複数の更新 Pull Request が
  同時にあるとき、検証は順に実行され、後続は待たされる。
- **本体の変更と更新 Pull Request が競合する**: 更新 Pull Request が作られた後に
  main が進んだ場合、更新 Pull Request は最新の main に対して再検証される。
- **非公開モジュールを解決できない**: 依存に非公開のモジュールが含まれる場合、
  更新の検出そのものに認証が必要である。認証が成立しなければ、その種別の更新は
  1 件も提案されない。**「提案がない」と「更新がない」は区別できる状態でなければ
  ならない。**
- **秘密情報を必要とする検査**: 依存更新 Pull Request による実行では、通常の検査で
  使う秘密情報が既定では利用できない。この状態では憲章が必須とする検査が実行できず、
  「検査が緑」と「検査が行われた」が食い違う。
- **更新対象に CI で用いるツール自体が含まれる**: CI が使うアクションやツールの
  更新は、その更新後の CI で検証される。壊れた更新は CI の失敗として現れる。
- **待機期間が長すぎる場合**: 脆弱性の修正版が待機期間に阻まれると、修正の適用が
  遅れる。脆弱性に対する更新は待機期間の対象外とする。

## Requirements *(mandatory)*

### Functional Requirements

#### 更新の検出と提案

- **FR-001**: システムは、依存パッケージの更新可能な版を定期的に検出し、更新を適用する Pull Request を自動で作成しなければならない。
- **FR-002**: システムは、版が公開されてから **5 日**が経過していない版への更新 Pull Request を作成してはならない。
- **FR-003**: システムは、既知の脆弱性に対する修正の適用については、FR-002 の待機期間を適用してはならない。修正の適用が遅れることの害が、待機によって得られる安全性を上回る。
- **FR-004**: システムは、Go モジュールの依存、GitHub Actions で使用するアクションの版、およびコンテナイメージのビルドに用いる基底イメージの版を、いずれも更新の対象としなければならない。
- **FR-005**: システムは、同じ種別の依存に対する複数の更新を 1 つの Pull Request にまとめなければならない。更新 1 件ごとに Pull Request を作ると、検証用ゾーンを共有する検査が直列に積み上がる。
- **FR-006**: システムは、更新 Pull Request の本文に、更新前後の版と変更内容の所在を含めなければならない。
- **FR-007**: システムは、互換性のない変更を含む版への更新も提案の対象としなければならない。提案から除外してはならない。取り込むかどうかは人が判断する。
- **FR-008**: システムは、同時に開く更新 Pull Request の数に上限を設けなければならない。上限がないと、検証用ゾーンを共有する検査の待ち行列が伸び続ける。

#### マージの扱い

- **FR-009**: システムは、更新 Pull Request を自動でマージしてはならない。マージは人のレビューと承認を経て行う。憲章「開発ワークフローと品質ゲート」がレビュー承認なしのマージを禁じている。
- **FR-010**: システムは、更新 Pull Request に対しても、通常の変更と同じ必須検査をマージの条件としなければならない。依存更新のために検査を減らした経路を設けてはならない。
- **FR-011**: システムは、自動でマージされなかった更新 Pull Request を自動で閉じてはならない。開いたまま残さなければならない。

#### 検査の実行可能性

- **FR-012**: システムは、更新 Pull Request に対して、秘密情報を必要としない検査を自動で実行しなければならない。整形、SPDX ヘッダ、シークレットの混入検査、ワークフローの静的検査が含まれる。
- **FR-013**: システムは、依存パッケージのコードを実行する検査 (テスト、ビルド) と、検証用ゾーンのアクセストークンを、**同じ実行の中に同居させてはならない。** 更新後の依存コードがトークンを読み取る経路を作らないため。
- **FR-014**: システムは、秘密情報を必要とする検査が更新 Pull Request の文脈で実行できない場合、その事実を「未実行」または「失敗」として明示しなければならない。成功として扱ってはならない。
- **FR-015**: システムは、保守担当者が更新内容を確認した後に、憲章が必須とする検査すべて (実際の DPF に対する追加・変更・削除の検証を含む) を実行できる手段を備えなければならない。
- **FR-016**: システムは、実際の DPF に対する検証を並列に実行してはならない。複数の更新 Pull Request があるときは順に実行しなければならない。

#### 更新の検出に必要な資格情報

- **FR-017**: システムは、更新の検出が停止している場合に、**その事実が保守担当者に伝わらなければならない。**「更新がない」と誤解される状態にしてはならない。

  > `github.com/iij/dpf-go` は 2026-09-14 に公開された。モジュールの取得に資格情報は要らず、
  > 本項のうち非公開モジュールに関する部分は解消している。検出の停止を伝える要件は残る。

#### 滞留の可視化

- **FR-018**: システムは、一定期間マージされていない更新 Pull Request があることを、保守担当者に伝えなければならない。
- **FR-019**: システムは、自動でマージされなかった理由 (どの検査が失敗したか、競合しているか、未実行の検査があるか) が Pull Request から判別できる状態を保たなければならない。

### Key Entities

- **依存の更新**: 1 つの依存パッケージを、ある版から別の版へ変える提案。対象の依存、更新前の版、更新後の版、版の公開日、更新の大きさ (互換性のない変更を含むか) を持つ。
- **待機期間**: 版が公開されてから、その版への更新を提案してよくなるまでの日数。汚染された版や誤って公開された版が取り下げられるまでの猶予として置く。
- **必須検査**: 更新をマージするために成功していなければならない検査の集合。憲章「開発ワークフローと品質ゲート」および「実環境での検証」が定める内容と一致する。
- **検証用ゾーン**: 実際の DPF に対する検証で破壊的操作を行う対象。複数の検査が共有するため、同時に使えない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 依存パッケージに更新可能な版があることを保守担当者が知るために行う操作が **0 回**である。
- **SC-002**: 更新を提案する Pull Request が、版の公開から **5 日未満**に作られる件数が **0 件**である。
- **SC-003**: 既知の脆弱性に対する修正が、公開から **1 日以内**に更新 Pull Request として提案される。
- **SC-004**: 必須検査を経ずに main へ入った変更が **0 件**である。
- **SC-005**: 更新後の依存コードと、検証用ゾーンのアクセストークンが同じ実行に同居した回数が **0 回**である。
- **SC-006**: 検証用ゾーンに対する検証が同時に 2 つ以上実行された回数が **0 回**である。
- **SC-007**: 更新 Pull Request を取り込むかどうかの判断に、保守担当者が Pull Request の外を参照する必要がない (判断材料が Pull Request 上で揃っている)。
- **SC-008**: マージされずに **30 日**を超えて放置された更新 Pull Request が、保守担当者に認識されていない状態で存在する件数が **0 件**である。
- **SC-009**: 資格情報の不足によって更新の検出が行われていない種別が、保守担当者に認識されていない状態で存在する件数が **0 件**である。

## Assumptions

### 既定として採った判断

- **更新の検出間隔は週 1 回**とする。日次では、待機期間 5 日と組み合わせても Pull Request の発生が細かくなりすぎる。週 1 回であれば、待機期間を満たした更新がまとまって提案される。
- **更新の対象は Go モジュール、GitHub Actions、コンテナ基底イメージの 3 種**とする。リポジトリに存在する依存の記述はこの 3 つである。
- **まとめ方は種別ごと**とする。Go モジュールの更新群、アクションの更新群、基底イメージの更新群をそれぞれ 1 つの Pull Request にまとめる。種別をまたいでまとめると、失敗したときに切り分けが難しくなる。
- **待機期間は更新の大きさによらず一律 5 日**とする。指示が「cooldown は 5 日間」であり、大きさによる区別は求められていない。区別を入れると、どの版がいつ提案されるかを保守担当者が予測しにくくなる。
- **更新後の依存コードを実行する検査には、秘密情報を与えない。** 本機能の動機は
  汚染されたパッケージへの備えである。汚染された版のコードが検証用ゾーンの
  トークンを読み取れる状態にしては、待機期間を置く意味が薄れる。実際の DPF に
  対する検証は、保守担当者が差分を確認した後に、信頼できる文脈で実行する
  (FR-013、FR-015)。

### 依存する前提

- **非公開モジュール `github.com/iij/dpf-go` の解決に認証が必要である。** これは
  更新の検出そのものに影響していた。**2026-09-14 に公開されたため、この前提は
  消えた。** モジュールの取得に認証は要らない。検出の停止を把握できる状態が
  要る点は変わらない (FR-017)。
- 実際の DPF に対する検証には、検証用ゾーンのアクセストークンとゾーン名が必要である
  (T102 で設定済み)。
- 検証用ゾーンは共有される状態であり、他の検査と同時に使えない (憲章「実環境での検証」)。
- 依存更新 Pull Request による実行は、通常の実行と同じ秘密情報を参照できない。
  これは実行環境側の仕様であり、本機能の設計で変えられるものではない。

### 範囲外

- **自動マージは範囲外**とする。当初の指示に含まれていたが、後に除外された。
  マージは人のレビューと承認を経る (FR-009)。憲章の改訂も不要になった。
- 依存の版を固定する方針 (どの依存を更新しないか) の見直しは範囲外。
- 更新によって生じた不具合の自動的な切り戻しは範囲外。
