# Data Model: 依存パッケージの更新 Pull Request の自動作成

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-09

本機能はデータを永続化しない。ここで定めるのは、設定と検査が扱う概念と、
それらの間の規則である。

---

## 1. 更新の提案 (Update Proposal)

依存 1 つ、または種別内の依存の集合を、ある版から別の版へ変える提案。
実体は Pull Request である。

| 項目 | 内容 |
|---|---|
| 種別 | `gomod` / `github-actions` / `docker` のいずれか |
| 対象 | 更新する依存の一覧 (まとめられるため複数になりうる) |
| 更新前の版 | 依存ごと |
| 更新後の版 | 依存ごと |
| 版の公開日 | 待機期間の判定に使う。Dependabot が保持する |
| 起点 | `dependabot[bot]` または保守担当者。**検査に使える秘密情報がこれで決まる** |
| 経過日数 | 作成からの日数。滞留の判定に使う |

### 状態

```
        (更新可能な版を検出)
                 │
                 ▼
        ┌─────────────────┐  版の公開から 5 日未満
        │  待機中          │◄────────────────────────
        └────────┬────────┘
                 │ 5 日経過 (脆弱性の修正は待機しない)
                 ▼
        ┌─────────────────┐
        │  提案 (PR)       │  起点 = dependabot[bot]
        │  秘密情報なし     │  秘密情報を要する検査は失敗する
        └────────┬────────┘
                 │ 保守担当者が上流の差分を確認し、コミットを積む
                 ▼
        ┌─────────────────┐
        │  検証済み         │  起点 = 保守担当者
        │  全検査が実行可能  │  必須検査がすべて Pull Request に紐づく
        └────────┬────────┘
                 │ レビュー承認 + 必須検査すべて成功
                 ▼
        ┌─────────────────┐
        │  マージ済み       │
        └─────────────────┘

  「提案」または「検証済み」のまま 30 日を超えた場合 → 滞留として報告
```

**「提案」から「マージ済み」へ直行する経路はない (FR-009)。** レビュー承認と
必須検査の成功が条件として間に入る。

**自動で「閉じた」状態へ遷移させない (FR-011)。** 閉じても更新の必要は消えず、
次の検出で同じ提案が作られる。

---

## 2. 待機期間 (Cooldown)

版が公開されてから、その版への更新を提案してよくなるまでの日数。

| 項目 | 値 | 根拠 |
|---|---|---|
| 日数 | **5** | 指示。汚染された版や誤って公開された版が取り下げられる窓を避ける |
| 適用範囲 | バージョン更新のみ | セキュリティ更新には適用されない (Dependabot の仕様、research R1) |
| 更新の大きさによる区別 | なし | `github-actions` と `docker` が対応しないため揃えられない (research R1) |

### 不変条件

- 待機期間は**設定として明示する**こと。省略すると既定の 3 日になり、要件と
  食い違う。テストで固定する (FR-002)
- セキュリティ更新に待機期間を適用しないこと。Dependabot の仕様によりこちらで
  何も書かなくても満たされるが、**待機期間をセキュリティ更新にも広げる設定を
  書かないこと** (FR-003)
- **セキュリティ更新そのものが有効であること。** 無効なら該当の Pull Request が
  1 件も作られず、FR-003 は空虚に満たされる一方 SC-003 は成立しない。
  下記「設定の所在」を参照 (research R8)

---

## 2.1 設定の所在 (Where Settings Live)

**本機能の設定は 2 か所に分かれる。** 片方しか見ないと欠落に気付けない。

| 設定 | 所在 | 対応する要件 | 機械的に検査できるか |
|---|---|---|---|
| バージョン更新の対象・待機期間・まとめ・上限 | `.github/dependabot.yml` | FR-001、FR-002、FR-004〜FR-008 | **できる** (`test/config/`) |
| **Dependabot alerts / security updates の有効化** | **リポジトリ設定** | **FR-003、SC-003** | **できない** |
| ブランチ保護 (必須検査 + レビュー承認) | リポジトリ設定 | FR-009、FR-010 | **できない** |

### 不変条件

- リポジトリ設定にあたる項目を、`.github/dependabot.yml` で表現しようとしない
  こと。セキュリティ更新を有効にする項目はこの設定ファイルに存在しない
- **検査できない項目は quickstart の確認手順に置くこと。** 「テストが緑」と
  「設定が正しい」が食い違う範囲を、文書の側で明示する (原則 V)

---

## 3. 必須検査の集合 (Required Checks)

更新をマージするために成功していなければならない検査。**通常の変更と同一である。**
依存更新のために減らした集合を作らない (FR-010)。

| 検査 | 秘密情報を要するか | 更新 PR による実行での結果 |
|---|---|---|
| シークレットの混入検査 (`betterleaks`) | 不要 | 実行される |
| 整形 (`gofmt -l`) | 不要 | 実行される |
| SPDX ヘッダ | 不要 | 実行される |
| ワークフローの静的検査 (`actionlint`) | 不要 | 実行される |
| 設定の不変条件 (本機能で追加) | 不要 | 実行される |
| ビルド (`go build`) | 不要 | 実行される |
| 静的解析 (`golangci-lint`) | 不要 | 実行される |
| 脆弱性検査 (`govulncheck`) | 不要 | 実行される |
| 全テスト (`go test`) | 不要 | 実行される |
| 契約テスト | 不要 | 実行される |
| 既定設定の検証 | 不要 | 実行される |
| ASLR の検証 | 不要 | 実行される |
| イメージのビルドと走査 | 不要 | 実行される |
| 依存ライセンスの検査 | 不要 | 実行される |
| 実際の DPF に対する検証 (`e2e`) | **要** (`DPF_TOKEN`) | **失敗する** |

> `github.com/iij/dpf-go` の公開 (2026-09-14) により、モジュール取得の認証が
> 不要になった。Go の検査とイメージのビルドは Dependabot 起点の実行でも通る。
> 実際の DPF に対する検証だけが `DPF_TOKEN` を要し、依然として失敗する。

### 不変条件

- **秘密情報が無いことを理由に検査を飛ばさないこと (FR-014)。** 飛ばした検査は
  「skipped」となり、ブランチ保護では成功として数えられる。検査を経ずに
  マージできる状態が生まれる (SC-004)
- 失敗の理由が読めること。「秘密情報が無いため実行できない」と、
  「更新によって壊れた」は区別できなければならない (FR-019)

---

## 4. 資格情報の区分 (Credential Scopes)

**本機能で最も重要な区分である。** 名前を分けることが設計上の要件になっている。

| 名前 | 種別 | 参照する場所 | 更新 PR の実行環境に現れるか |
|---|---|---|---|
| `DPF_TOKEN` | Actions secret | `e2e.yml` / `e2e-sidecar.yml` | 現れない。Dependabot 起点では空になる |

`DPF_GO_READ_TOKEN` と `MODULE_TOKEN` は `dpf-go` の公開により不要になり、
いずれも用いない。

### 不変条件

- `DPF_TOKEN` を **Dependabot secret として登録しないこと。** 登録すると
  Dependabot 起点の実行で使えるようになり、更新後の依存コードから届く (FR-013)
- モジュール取得のための資格情報を新たに設けないこと。`dpf-go` は公開済みである

---

## 5. 滞留の判定 (Staleness)

| 項目 | 値 | 根拠 |
|---|---|---|
| 滞留とみなす日数 | **30** | SC-008 |
| 判定の対象 | 開いている Dependabot の Pull Request | |
| 報告先 | 既存の `scheduled.yml` の通知経路 (Issue) | 通知手段を増やさない (research R5) |

---

## 6. 提案の欠落の判定 (Missing Proposals)

「更新がない」と「提案の仕組みが動いていない」を区別するための照合。

| 項目 | 内容 |
|---|---|
| 期待側 | `go list -m -u all` が示す更新可能な直接依存 |
| 実際側 | 開いている Dependabot の Pull Request が含む依存 |
| 判定 | 期待側にあって実際側にないものが**待機期間を超えて**存在すれば異常 |
| 報告先 | 滞留と同じ通知経路 |

### 不変条件

- 待機期間内の版を「提案されていない」と誤って報告しないこと。5 日以内に
  公開された版は、提案されないのが正しい (FR-002)
- この照合は Dependabot に依存しない側から行うこと。Dependabot の実行状態を
  問い合わせる公開 API はない (research R4)
