# Feature Specification: ExternalDNS webhook provider 本体

**Feature Branch**: `feature/create-webook`

**Created**: 2026-09-04

**Status**: Draft

**Input**: User description: "webhook provider 本体（一括）— ExternalDNS webhook API の4エンドポイント（ネゴシエーション、レコード取得、調整、適用）＋ IIJ DNSプラットフォームサービス (DPF) によるレコード CRUD。最小構成で end-to-end に動くもの。"

## User Scenarios & Testing *(mandatory)*

本機能の直接の利用者は 2 者いる。**クラスタ運用者** (Kubernetes に ExternalDNS と本 provider を
導入し、DNS レコードを自動管理させたい人) と、**ExternalDNS** (本 provider を呼び出す
システム) である。DNS レコードの実体は **IIJ DPF** が保持する。

### User Story 1 - 管理対象の宣言とレコードの把握 (Priority: P1)

クラスタ運用者は、本 provider に「どのドメインを管理させるか」を設定して起動する。
ExternalDNS は起動時に本 provider へ問い合わせ、管理対象ドメインの範囲を知る。続いて
現在 DPF に登録されているレコードの一覧を取得し、あるべき状態との差分計算に用いる。

**Why this priority**: 管理範囲の宣言と現状の読み取りができなければ、ExternalDNS は差分を
計算できず、後続のいかなる操作も成立しない。また、この段階までは DNS を一切変更しないため、
本番ゾーンに対しても安全に検証できる。単独でも「DPF の内容を ExternalDNS から参照できる」
という価値を持つ。

**Independent Test**: 本 provider を起動し、ExternalDNS から管理対象ドメインの問い合わせと
レコード一覧の取得を行う。DPF に登録済みのレコードが漏れなく、かつ管理対象外のレコードを
含まずに返ることを確認する。DNS への書き込みは発生しない。

**Acceptance Scenarios**:

1. **Given** 管理対象ドメインとして `example.jp` が設定されている、**When** ExternalDNS が
   管理対象ドメインを問い合わせる、**Then** `example.jp` が管理対象として返る
2. **Given** 管理対象ドメインが 1 つも設定されていない、**When** ExternalDNS が管理対象
   ドメインを問い合わせる、**Then** 管理対象が空であると返り、以降レコードは 1 件も
   管理対象として扱われない
3. **Given** DPF に `example.jp` と `other.jp` のレコードが存在し、管理対象が `example.jp`
   のみである、**When** ExternalDNS がレコード一覧を取得する、**Then** `example.jp` に
   属するレコードのみが返り、`other.jp` のレコードは含まれない
4. **Given** DPF に `WWW.Example.JP` として登録されたレコードが存在する、**When**
   ExternalDNS がレコード一覧を取得する、**Then** 大文字小文字の違いによらず
   `example.jp` の管理対象レコードとして返る
5. **Given** DPF API が一時的に応答しない、**When** ExternalDNS がレコード一覧を取得する、
   **Then** 一時的な障害であることが伝わる形で失敗し、ExternalDNS が再試行できる

---

### User Story 2 - レコードの作成・更新・削除 (Priority: P2)

クラスタ運用者が Ingress や Service を作成・変更・削除すると、ExternalDNS が差分を計算し、
本 provider に変更内容を渡す。本 provider はそれを DPF に反映し、名前解決が実際に変わる。

**Why this priority**: 本機能の中心的な価値であり、これが動いて初めて「DNS レコードの
自動管理」が成立する。一方で DNS を破壊しうる唯一の経路でもあるため、読み取り (US1) が
確立した後に着手する。

**Independent Test**: 検証用ゾーンに対して、レコードの作成・更新・削除をそれぞれ実行し、
DPF 上の状態が期待どおりに変わることを確認する。同じ変更を 2 回適用しても結果が
変わらないことを確認する。

**Acceptance Scenarios**:

1. **Given** `app.example.jp` のレコードが存在しない、**When** ExternalDNS が当該レコードの
   作成を要求する、**Then** DPF に作成され、名前解決できる状態になる
2. **Given** `app.example.jp` が既存の値で登録されている、**When** ExternalDNS が別の値への
   更新を要求する、**Then** DPF 上の値が新しい値に置き換わる
3. **Given** `app.example.jp` が登録されている、**When** ExternalDNS が当該レコードの削除を
   要求する、**Then** DPF から削除される
4. **Given** ある変更セットの適用が既に成功している、**When** 同一の変更セットが再度
   適用される、**Then** DPF の最終状態は変わらず、エラーにもならない
5. **Given** 管理対象外のドメインに属するレコードの変更が要求された、**When** 適用を試みる、
   **Then** そのレコードは変更されず、DPF 上の管理対象外レコードは一切影響を受けない
6. **Given** 変更セットの適用中に DPF API がエラーを返した、**When** 適用が中断される、
   **Then** 成功として扱われず、ExternalDNS に失敗が伝わる
7. **Given** DPF が変更の反映に明示的な適用操作を要求する、**When** 変更セットを適用する、
   **Then** 反映が完了するまでを 1 つの操作として扱い、未反映の状態で成功を返さない

---

### User Story 3 - DPF の制約に合わせたレコードの調整 (Priority: P3)

ExternalDNS が算出したあるべきレコードが、そのままでは DPF に登録できない場合がある。
本 provider は適用前に、DPF の制約に合わせた調整を行い、調整後の内容を ExternalDNS に返す。
ExternalDNS はこれを踏まえて差分を計算するため、毎回同じ差分が繰り返し検出される状態
(差分の振動) を防げる。

**Why this priority**: これがないと、ExternalDNS が「まだ差分がある」と判断し続け、同じ変更を
無限に再適用する。US1・US2 が動いた後に顕在化する問題であり、単独では価値が完結しない。

**Independent Test**: DPF の制約に抵触する内容 (例: 下限を下回る TTL) を含むレコードを
調整に掛け、DPF が受け付ける形に補正されて返ることを確認する。調整結果を再度調整に
掛けても内容が変わらないことを確認する。

**Acceptance Scenarios**:

1. **Given** DPF が許容しない TTL を持つレコードが渡された、**When** 調整を要求する、
   **Then** DPF が受け付ける範囲に補正された内容が返る
2. **Given** 既に調整済みのレコードが渡された、**When** 再度調整を要求する、**Then**
   内容は変化しない
3. **Given** 調整の必要がないレコードが渡された、**When** 調整を要求する、**Then**
   渡された内容がそのまま返る

---

### User Story 4 - 運用状態の把握と障害の切り分け (Priority: P3)

クラスタ運用者は、本 provider が正常に動いているか、DNS の更新が成功しているかを知りたい。
問題が起きたとき、原因が ExternalDNS 側にあるのか、本 provider にあるのか、DPF 側にあるのかを
切り分けたい。

**Why this priority**: サイドカーとして無人で動作するため、状態が見えないと運用できない。
ただし US1・US2 が動いていない段階では観測する対象がないため、優先度は P3 とする。

**Independent Test**: 本 provider を起動し、稼働状態の確認、レコード変更操作の成否と件数の
計測、および 1 回のレコード取得要求が DPF 呼び出しまで追跡できることを確認する。

**Acceptance Scenarios**:

1. **Given** 本 provider が起動している、**When** 稼働状態を確認する、**Then** 正常である
   ことが分かる
2. **Given** レコードの変更操作が行われた、**When** 計測値を参照する、**Then** 操作の成否と
   件数が分かる
3. **Given** DPF API がエラーを返した、**When** ログを参照する、**Then** どのゾーンの
   どの操作が、どの理由で失敗したかが分かる
4. **Given** 認証情報が設定されている、**When** ログ・計測値・トレースのいずれを参照しても、
   **Then** 認証情報の値は含まれない
5. **Given** テレメトリの送出先が到達不能である、**When** レコードの変更が要求される、
   **Then** 変更処理は継続され、DNS の更新は妨げられない

---

### Edge Cases

- 管理対象ドメインが未設定のまま起動した場合、レコードは 1 件も管理対象とならない
  (全件管理にはならない)
- 必須の設定 (DPF の認証情報など) が欠けている場合、起動せずに異常終了する
- `example.jp` を管理対象としたとき、`evil-example.jp` は管理対象に含まれない
  (ラベル境界での判定)
- 同一の名前が、末尾ドットの有無や大文字小文字の違いで別レコードとして重複作成されない
- ワイルドカードレコード (`*.example.jp`) が要求された場合の扱いが明示的に決まっている
- 空の変更セットが適用要求された場合、何も変更せず成功として扱う
- 対応リスト外のレコード種別が要求された場合、当該レコードは適用されず、その旨が分かる
- DPF 上に `CAA` や `ANAME` など管理対象外の種別のレコードが存在しても、
  それらが変更・削除されることはない
- ゾーン名と同じ名前の `NS` レコードの削除が要求されても、削除は行われない
- 名前にアンダースコアを含む `A` レコードの登録が要求された場合、DPF へ送る前に
  恒久的な失敗として扱われる
- 同一の名前に対して `CNAME` と他種別が同時に要求された場合、恒久的な失敗として扱われる
- 複数の character-string からなる `TXT` (例: `"STR1" "STR2"`) が、合計 255 オクテットを
  超えても正常に登録される。DKIM 鍵のような長い値がこれに該当する
- 255 オクテットを超える単一の character-string は、拒否されず自動的に分割されて登録される
- 分割の必要がない `TXT` を読み取って書き戻したとき、分割位置が変化しない
- 引用符を含まない `TXT` の値 (例: `v=spf1 -all`) が、空白で分割されずに登録される
- マウントされたトークンファイルが外部で書き換えられた場合、再起動なしに新しいトークンで
  DPF API を呼び出す
- トークンファイルが存在しない、またはシークレット管理サービスから取得できない場合、
  恒久的な失敗として扱われ、同じ要求を再試行し続けることはない
- トークンの取得に失敗したとき、エラーメッセージにトークンの値やファイルの内容が
  含まれない
- 適用の実行中に、ロックを取らない他者が同じゾーンを変更した場合、その変更は
  取り消されうる (利用前提条件 PC-002)。本 provider はこれを検出しない
- ゾーンに未反映の編集が残っている状態で適用が行われた場合、その編集は破棄される。
  適用は中止されない (FR-020a)
- ゾーンに 1,000 件規模のレコードが存在しても、適用が 1 回の操作として成立する
- 適用の実行中に、同じゾーンロックを取得しようとする他者は待たされる。
  ロックは適用の完了時に解放され、異常終了時も有効期限で解放される
- DPF API がレート制限を返した場合、一時的な障害として扱われ再試行が可能である
- DPF 上のゾーンが存在しない、または本 provider の権限では操作できない場合、
  恒久的な失敗として扱われる
- 1 つの変更セットに、成功するものと失敗するものが混在した場合、成功として扱わない
- 管理対象ゾーンが DPF 上に存在しない場合、本 provider はゾーンを作成しない

## Requirements *(mandatory)*

### Functional Requirements

**管理対象の決定**

- **FR-001**: システムは、設定された管理対象ドメインを ExternalDNS に通知できなければならない
- **FR-002**: システムは、管理対象ドメインが未設定の場合、いかなるレコードも管理対象として
  扱ってはならない
- **FR-003**: システムは、あるレコードが管理対象に含まれるかをドメイン名のラベル境界で
  判定しなければならない。文字列としての部分一致で判定してはならない
- **FR-004**: システムは、ドメイン名を大文字小文字の違いおよび末尾ドットの有無によらず
  同一の名前として扱わなければならない

**レコードの読み取り**

- **FR-005**: システムは、管理対象ドメインに属する DNS レコードの一覧を DPF から取得し、
  ExternalDNS に返せなければならない
- **FR-006**: システムは、管理対象外のレコードを一覧に含めてはならない
- **FR-007**: システムは、複数の管理対象ゾーンを同時に扱えなければならない

**レコードの変更**

- **FR-008**: システムは、ExternalDNS から受け取った変更セットに基づき、DNS レコードを
  作成・更新・削除できなければならない
- **FR-009**: システムは、管理対象外のレコードを変更・削除してはならない
- **FR-010**: システムは、同一の変更セットが複数回適用されても、最終状態が変わらず、
  追加の副作用を生じさせてはならない
- **FR-011**: システムは、変更の反映が完了する前に成功を返してはならない
- **FR-012**: システムは、変更セットの適用が部分的にしか成功しなかった場合、成功として
  返してはならない
- **FR-013**: システムは、管理対象ゾーンを自ら作成してはならない。ゾーンは事前に DPF 上に
  存在することを前提とする

**調整**

- **FR-014**: システムは、ExternalDNS が算出したレコードを、DPF が受け付ける形に調整して
  返せなければならない
- **FR-015**: 調整は冪等でなければならない。調整済みの内容を再度調整しても結果が
  変わってはならない

**資格情報の受け渡し**

- **FR-034**: クラスタ運用者は、DPF のアクセストークンを、マウントされたファイルとして
  与えられなければならない
- **FR-035**: クラスタ運用者は、DPF のアクセストークンを、外部のシークレット管理サービス
  から取得させられなければならない
- **FR-036**: システムは、上記 2 経路以外からトークンを受け取ってはならない。
  特に、環境変数およびコマンドライン引数からトークンを受け取ってはならない
- **FR-037**: システムは、トークンが外部でローテーションされた場合、再起動なしに新しい
  トークンを使わなければならない
- **FR-038**: システムは、トークンの取得に失敗した場合、恒久的な失敗として扱わなければ
  ならない。取得できない状態は再試行では解消しないため、再試行を繰り返してはならない
- **FR-039**: システムは、トークンの値、およびトークンを含むファイルの内容を、
  エラーメッセージに含めてはならない

**エラーの扱い**

- **FR-016**: システムは、一時的な障害と恒久的な障害を区別して ExternalDNS に伝えなければ
  ならない。ExternalDNS が再試行すべきかを判断できる必要がある
- **FR-017**: システムは、必須設定が欠けた状態で起動してはならない
- **FR-018**: システムは、設定値の解釈に失敗した場合、既定値で起動を続行してはならない

**可観測性**

- **FR-019**: システムは、稼働状態を外部から確認できなければならない
- **FR-020**: システムは、DNS レコードの変更操作について、対象・操作種別・結果を記録
  しなければならない
- **FR-020a**: システムは、ゾーンに未反映の編集が存在することを理由に、適用を中止しては
  ならない。未反映の編集の有無を調べてはならない (利用前提条件 PC-004)
- **FR-021**: システムは、レコード変更操作の成否と件数を計測値として提供しなければならない
- **FR-022**: システムは、ExternalDNS からの要求受信から DPF 呼び出しまでを 1 つの流れとして
  追跡可能にしなければならない
- **FR-023**: システムは、認証情報を記録・計測値・追跡情報のいずれにも含めてはならない
- **FR-024**: システムは、テレメトリの送出に失敗しても、DNS レコードの処理を停止しては
  ならない

**対応レコード種別**

- **FR-025**: システムは、対応するレコード種別を明示的な許可リストとして扱い、
  未対応の種別を暗黙に通過させてはならない
- **FR-026**: システムは、次の 9 種別を対応レコード種別としなければならない:
  `A`, `AAAA`, `CNAME`, `TXT`, `SRV`, `NS`, `PTR`, `MX`, `NAPTR`。
  これは ExternalDNS が表現できる種別と DPF が提供する種別の交差である
- **FR-027**: システムは、DPF が提供するが ExternalDNS が表現できない種別
  (`SOA`, `CAA`, `TLSA`, `DS`, `SVCB`, `HTTPS`, `ANAME`) を管理対象として扱っては
  ならない。これらが DPF 上に存在しても、変更・削除してはならない
- **FR-028**: システムは、対応リスト外の種別を含む変更が要求された場合、当該レコードを
  適用せず、恒久的な失敗として扱わなければならない

**DPF 由来のレコード制約**

DPF は種別ごとに登録可能な形を制限する。システムはこれらを満たさない要求を DPF へ
送る前に検出し、調整可能なものは調整し、調整できないものは恒久的な失敗として扱う。

- **FR-029**: システムは、ゾーン名と同じ名前の `NS` レコードを削除してはならない。
  DPF が削除を許さないため、削除要求が来ても実行してはならない
- **FR-030**: システムは、`CNAME` について、同一の名前に複数の値を登録してはならず、
  同一の名前に他の種別と共存させてはならない。これに反する要求は恒久的な失敗として
  扱わなければならない
- **FR-031**: システムは、名前にアンダースコア (`_`) を含む `A` および `AAAA` レコードの
  登録を試みてはならない。DPF が許可しないため、恒久的な失敗として扱わなければならない
- **FR-032**: システムは、`TXT` の character-string が 255 オクテットを超える場合、
  **255 オクテット以下の複数の character-string へ自動的に分割しなければならない**。
  長すぎることを理由に失敗としてはならない。1 つの `TXT` レコードは複数の
  character-string を持つことができ、その**合計長が 255 オクテットを超えることは
  正常である**。合計長を理由に失敗としてはならない
- **FR-032a**: システムは、分割の必要がない `TXT` の値を書き換えてはならない。
  読み取り時に連結して 1 つの character-string にしてはならず、書き込み時に
  分割位置を変えてはならない。書き換えるのは FR-032 の自動分割が必要な場合に限る
- **FR-032b**: システムは、引用符を含まない `TXT` の値を、全体で 1 つの
  character-string として扱わなければならない。空白で分割してはならない。
  複数の character-string は受信側で連結して解釈されるため、分割すると
  値の意味が変わる
- **FR-033**: システムは、`MX` の preference、`SRV` の priority・weight・port が
  0〜65535 の範囲外である要求を、恒久的な失敗として扱わなければならない

### Key Entities

- **管理対象ドメイン (ドメインフィルタ)**: 本 provider が操作を許される名前の範囲。
  未設定は「範囲なし」を意味する
- **管理対象ゾーン**: DPF 上に存在し、本 provider が操作するゾーン。事前に作成されている
  ことを前提とする
- **DNS レコード**: 名前、種別、値の集合、TTL を持つ。ExternalDNS 側の表現と DPF 側の表現の
  双方が存在し、相互に変換される
- **変更セット**: ExternalDNS が算出した、作成・更新・削除の対象レコードのまとまり。
  適用は変更セット単位で成否が決まる
- **DPF 資格情報 (アクセストークン)**: DPF API を操作するための認証情報。マウントされた
  ファイル、または外部のシークレット管理サービスから取得される。外部でローテーション
  されうるため、固定値ではなく「その時点で取得できる値」として扱う。記録されない

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: クラスタ運用者が Ingress を作成してから、対象ホスト名が DPF 上のレコードとして
  反映されるまで、5 分以内に完了する
- **SC-002**: 同一の変更セットを 10 回連続で適用しても、DNS の最終状態が 100% 変わらない
- **SC-003**: 管理対象ドメインを未設定にした状態で稼働させたとき、DPF 上のレコードが
  変更される件数が 0 件である
- **SC-004**: 管理対象外のゾーンに属するレコードが変更・削除される件数が、いかなる操作でも
  0 件である
- **SC-005**: DNS 更新の失敗が発生したとき、運用者はログのみで、失敗した対象と原因の所在
  (本 provider 側か DPF 側か) を特定できる
- **SC-006**: 認証情報が、ログ・計測値・追跡情報・エラーメッセージのいずれにも
  1 件も出現しない
- **SC-009**: トークンを外部でローテーションした後、本 provider を再起動することなく、
  DNS の更新が継続して成功する
- **SC-007**: ExternalDNS が同一の差分を繰り返し検出し続ける状態 (差分の振動) が発生しない
- **SC-008**: 管理対象ゾーンに 1,000 件のレコードが存在する状態でも、レコード一覧の取得が
  ExternalDNS の待ち受け時間内に完了する

## 利用前提条件

本 provider は、変更の適用時にゾーンの現在の内容を読み取り、変更を反映した内容を
書き戻す。この読み取りと書き戻しの間に他者が同じゾーンを変更すると、その変更は
書き戻しによって取り消される。区間はゾーンロックで保護されるが、**ロックを取らない
変更者に対しては効果がない。**

したがって、本 provider を導入するゾーンには次の前提が要る。

- **PC-001**: 同一ゾーンを本 provider 以外の**機械的な手段**で変更する場合、その手段は
  次のいずれかを満たさなければならない。
  - **(a) 同じゾーンロックを取得してから変更する。** 本 provider が用いるものと同一の
    排他機構に参加する
  - **(b) あるべき状態へ継続的に収束させる。** 変更が一時的に取り消されても、次の周回で
    再度適用される仕組みを持つ
- **PC-002**: 上記いずれも満たさない機械的な変更は、本 provider の適用と競合したとき、
  黙って取り消されることがある。この損失は本 provider では検出も防止もできない
- **PC-003**: 人手による変更 (DPF コンソールでの操作など) も、適用の区間に重なれば
  同様に取り消されうる。頻度は低いが、原理的には同じである
- **PC-004**: 本 provider が管理するゾーンに、**未反映の編集 (保留変更) を残さないこと。**
  適用はゾーンの内容を置き換えるため、その時点で存在した保留変更は**破棄される**。
  権威 DNS へ公開されることはないが、編集作業そのものが失われる。
  DPF コンソールでの作業を途中で中断したまま放置しない運用が必要である。
  なお、破棄の記録は DPF サービス側のログに残るため、本 provider はこれを検出も
  記録もしない

本 provider 自身は (b) を満たす。ExternalDNS があるべき状態を周期的に再計算するため、
本 provider の変更が他者に取り消されても、次の周回で再適用される。

**この前提を満たせない場合**: 本 provider に管理させるゾーンを、他の機械的な変更者と
共有しないこと。ゾーンを分けるのが最も確実である。

## Assumptions

- 本 provider は ExternalDNS と同一 Pod 内のサイドカーとして動作する。ExternalDNS 以外からの
  呼び出しは想定しない
- ExternalDNS 本体のバージョンは v0.22.0 以降を対象とする (constitution v1.7.0 に準拠)
- 管理対象ゾーンは DPF 上に事前に作成済みである。ゾーンの作成・削除は本機能の範囲外とする
- DPF の契約・アカウント管理、および API 利用権限の付与は、本機能の範囲外とする
- レコードの所有権管理 (どのレコードが ExternalDNS 由来かの記録) は ExternalDNS 本体の
  registry 機能が担い、本 provider は関与しない
- 単一の DPF 資格情報で、管理対象となる全ゾーンを操作できるものとする
- DPF API へのアクセスは `github.com/iij/dpf-go` が担う (constitution v1.8.0)。
  同ライブラリはトークンをファイルおよび任意の取得処理から供給でき、リクエストごとに
  評価するため、FR-037 のローテーション追随はライブラリの仕組みに乗る
- 対応するシークレット管理サービスは、`dpf-go` が別モジュールとして提供する範囲
  (HashiCorp Vault、AWS Secrets Manager、Azure Key Vault、Google Secret Manager) を
  上限とする。これ以外のサービスへの対応は本機能の範囲外とする
- `github.com/iij/dpf-go` は本機能の完成後に公開される予定であり、開発期間中は非公開である。
  そのため開発・CI 環境では認証を伴うモジュール取得が必要になる。公開後は不要となる
- ExternalDNS が表現できる `DNAME` は、DPF のレコード種別一覧に記載がないため対象外とする。
  DPF が対応することが確認できた場合は、別途 spec の改訂で追加する
- DPF が提供する `ANAME` (独自種別) と `SVCB`/`HTTPS` は、ExternalDNS 側に対応する表現が
  ないため対象外とする。ゾーン apex の別名解決を ANAME で行いたい要件は本機能の範囲外とする
- ExternalDNS が dry-run 相当の確認を行う場合、その判断は ExternalDNS 側が担う。
  本 provider は独自の dry-run 機能を持たない
- 本機能の範囲は provider の振る舞いに限る。コンテナイメージの構成や NetworkPolicy
  などの配布・デプロイ成果物は、constitution が要件を定めるが、本 spec の対象外とする
- デプロイは上流の external-dns Helm チャートを経路とする (constitution v2.0.0)。
  本リポジトリで独自のチャートは維持しない。チャートへ与える推奨 values は
  README に示す

## Dependencies

- **ExternalDNS webhook provider API**: 本 provider の外部インタフェースは上流仕様に従う。
  仕様が変わった場合の追随可否は constitution の改訂を要する
- **IIJ DNSプラットフォームサービス (DPF) の DNS API**: レコードの読み取りと変更の実体。
  提供されるレコード種別、TTL の制約、変更の反映方式、レート制限が本機能の振る舞いを規定する。
  対応レコード種別と種別ごとの制約は DPF のマニュアル
  (<https://manual.iij.jp/dpf/help/19629152.html>) を典拠とする
- **`github.com/iij/dpf-go`**: DPF API クライアント。認証、ページング、レート制御、
  リトライ、非同期ジョブの完了待ちを担う。v1.0.0 到達前のため、マイナーバージョンの更新に
  破壊的変更を含みうる
- **シークレット管理サービス (任意)**: トークン取得に利用する場合のみ必要となる外部依存。
  利用しない構成では到達性を必要としない
- **同一ゾーンを操作する他の仕組み (存在する場合)**: 利用前提条件 PC-001 を満たす必要がある。
  満たさない場合、その仕組みの変更が失われうる
- **検証用の DPF ゾーン**: 受け入れ確認には、破壊的操作を行ってよい検証用ゾーンが必要である
