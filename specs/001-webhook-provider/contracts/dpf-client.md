# Contract: DPF クライアント層の内部境界

**Feature**: [../spec.md](../spec.md) | **Date**: 2026-09-04

原則 II (プロバイダ境界の分離) が求める境界の契約。`internal/provider` が
`internal/dpf` に期待する振る舞いを定義する。インタフェースは利用側
(`internal/provider/ports.go`) で宣言し、実装を `internal/dpf` が提供する。

**この境界の存在理由**: 上位層のテストが実際の DPF API に到達しないこと (原則 II の MUST)。
`dpf-go` の生成型とライブラリ固有のエラー型は、この境界を越えない。

---

## 越えてはならないもの

| 種別 | 例 | 扱い |
|---|---|---|
| 生成された API 型 | `dpf.Record`, `dpf.Zone`, `dpf.RecordsRrtype` | 境界の内側に留める |
| ライブラリ固有のエラー | `*dpf.GenericOpenAPIError`, `*utils.TokenError` | 境界で本プロジェクトのエラー型へ変換 |
| HTTP の詳細 | ステータスコード、ヘッダ、URL | 境界の内側に留める |
| 認証情報 | アクセストークン | 境界の内側に留める。上位層は存在を知らない |

上位層が受け取るのは、正規化名・許可リストの種別・値・TTL からなる本プロジェクトの型と、
後述の分類済みエラーのみ。

---

## 提供する操作

### ゾーンの解決

```
管理対象ゾーンの一覧を取得する
```

- 返すのは、正規化名とゾーン識別子の対応
- 名前は取得時点で正規化する (research R7)

### レコードの取得

```
指定ゾーンの、公開中のレコード一覧を取得する
```

- 全ページを取得する (`ExecuteAll` 相当)。ページングは境界の内側で完結させる
- 許可リスト外の種別は除外して返す (FR-027)
- 名前は正規化して返す

### 変更の適用

```
指定ゾーンに対し、変更セットを適用し、反映完了まで待つ
```

適用は次の順序で行い、**全体で 1 つの操作**として成否を返す。
この一連はすべて 1 回の適用要求の処理中に完結する。

1. ゾーンロックの取得
2. 反映済みレコードの全件取得 (**マージの土台をここで読み直す**)
3. マージ (管理対象は変更を適用、管理対象外は逐語コピー)
4. 投入前ガード
5. 一括更新とゾーン反映 (原子的に実行)
6. 反映完了の待ち合わせ
7. ロックの解放

**制約**:

- ロックの範囲はこの操作の内側に閉じる。**レコード取得の操作はロックしない (MUST NOT)。**
  webhook の取得要求と適用要求は独立しており、取得の後に適用が来る保証がないため、
  両者をまたいでロックを保持するとゾーンが操作不能になる (research R4)
- マージの土台は、渡された変更セットではなくこの操作内で読み直した現在値とする (MUST)。
  呼び出し側が以前に取得した一覧を土台に使わない (MUST NOT)
- 変更セットの「更新前の値」が現在値と一致しない場合も、「更新後の値」を適用する。
  一致を要求すると差分が解消せず振動する (SC-007、research R4)
- マージの土台には**反映済みレコードの一覧**を用いる (MUST)。編集中を含む一覧を
  用いない (MUST NOT)。後者を土台にすると、他者の未レビューの編集を取り込んで
  公開してしまう
- ゾーンに未反映の編集が存在しても適用を中止しない (MUST NOT)。中止する設計は、
  下書きの放置で適用が恒久的に停止する。**未反映の編集の有無を調べない (MUST NOT)。**
  検出には追加の API 呼び出しが必要で、得られる記録は DPF サービス側のログと
  重複する (research R3)
- 管理対象外のレコードは**逐語的にコピー**して投入する。本プロジェクトの型へ変換しない
  (MUST NOT)。変換の誤りが管理対象外のレコードを壊す経路を作らないため
- 投入する集合から失われるレコードが変更セットの削除対象と一致しない場合、
  適用を中止する (投入前ガード)
- SOA とゾーン apex の `NS` も投入する集合に含める (MUST)。省くと API が
  `soa_not_found` / `apex_ns_not_found` で拒否する
- `overwrite_soa` と `overwrite_zone_apex_ns` は**常に `false`** を明示して送る
  (MUST)。`true` を送らない (MUST NOT)。これにより投入した SOA / apex NS の値は
  取り込まれず、FR-029 が API 側で担保される (research R3)
- 反映完了前に成功を返さない (FR-011)
- 途中で中止した場合、成功を返さない (FR-012)。更新と反映は原子的であるため、
  中止時に巻き戻す保留状態は存在しない
- ロックは、成功・失敗のいずれの経路でも解放する

**この境界が隠すもの**: 上位層は「変更セットを渡す」だけであり、ゾーン全体を読んで
マージし直しているという実装事情を知らない。将来 DPF が差分適用の API を提供した場合、
この境界の内側だけを差し替えられる。

---

## エラーの分類

境界を越えるエラーは、**一時的か恒久的か**に分類済みでなければならない。
この分類が webhook 契約の `4xx` / `5xx` を決める。

| 分類 | 該当する状況 | 上位層での扱い |
|---|---|---|
| 一時的 | DPF の応答不能、レート制限、ロック取得不能、反映の時間切れ | `5xx` |
| 恒久的 | 形式違反、未対応種別、ゾーン解決不能、権限不足、トークン取得失敗 | `4xx` |

**トークン取得失敗は恒久的**として扱う。取得できない状態は同じ要求を繰り返しても
解消しないため (FR-038)。`dpf-go` の `TokenError` もライブラリ側でリトライされない
設計であり、この分類と一致する。

**エラーメッセージの制約**: トークンの値、およびトークンを含むファイルの内容を
含めない (FR-039)。

## テストでの差し替え

`dpf-go` は API をインタフェースとして公開しており (`interfaces.go` の
`dpf.RecordsApi` / `dpf.ZonesApi` など)、`utils` の関数もこれらを引数に取る。
したがって差し替えは 2 段階で可能である。

| 層 | 差し替え対象 | 用途 |
|---|---|---|
| `internal/provider` のテスト | 本書のインタフェース | 範囲判定・差分・調整の検証 |
| `internal/dpf` のテスト | `dpf.RecordsApi` / `dpf.ZonesApi` | 変換・エラー分類・適用手順の検証 |

いずれの層のテストも、実際の DPF API に到達しない。
