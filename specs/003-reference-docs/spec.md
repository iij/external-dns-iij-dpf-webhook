# Feature Specification: リファレンス文書

**Feature Branch**: `003-reference-docs`

**Created**: 2026-09-09

**Status**: Draft

**Input**: User description: "/metricsが提供するメトリクスの名前、種類、内容をREADME.mdから辿れるところにドキュメント化してください。" — 後に「シークレット管理サービスも、KMS を使った時に、どの key になるかが書いてないです。認証方法も不明なので、これもドキュメント化してください」「003 は metrics に限定せずリファレンス文書にしましょう」として、対象を外部から観測できる面の全体へ広げた。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 設定とトークンの置き場所を正しく知る (Priority: P1)

本サービスを導入する運用者が、シークレット管理サービスにアクセストークンを預けて
起動しようとしている。**シークレットのどこにトークンを置けばよいのか、何で認証されるのか、
どの権限を与えればよいのか**を、実装コードを読まずに知りたい。

**Why this priority**: これが分からないと**起動できない**。他のどの記述も、
サービスが動いていることを前提にしている。実際に「値をどう置くか」を誤ると、
認証に失敗する、あるいは黙って別の文字列をトークンとして送ることになる。

**Independent Test**: 実装コードを読んだことのない運用者が、文書だけを見て
4 つのシークレット管理サービスそれぞれにトークンを格納し、起動できるかで検証する。

**Acceptance Scenarios**:

1. **Given** 文書を開いた運用者、**When** 使いたいシークレット管理サービスの節を読む、**Then** 識別子に何を渡すか、シークレットのどこがトークンとして読まれるか、何で認証されるか、どの権限が必要かがすべて記載されている
2. **Given** シークレットの値の中の特定のフィールドが読まれるサービスがある、**When** その節を読む、**Then** **フィールド名**と、それが変更できるかどうかが記載されている
3. **Given** 同じ設定項目がサービスによって違う意味を持つ、**When** 文書を読む、**Then** サービスごとの意味の違いが明示されている
4. **Given** 文書に載っている格納の手順、**When** そのとおりに実行して起動する、**Then** 認証に成功する
5. **Given** 設定項目の一覧、**When** 実際に受け付けられる項目と突き合わせる、**Then** 記載のない項目も、記載があって存在しない項目もない

---

### User Story 2 - 観測した値の意味を知る (Priority: P2)

運用者が監視基盤で計測値を収集し、ログを集約し始めた。集まってきた系列が何を数えて
いるのか、エラーがどう分類されるのかを知りたい。

**Why this priority**: 収集はできても値を読めなければ、観測を提供している意味が
運用者に届かない。US1 と違い、これができなくてもサービスは動く。

**Independent Test**: 実装コードを読まずに、文書だけを見て「DNS レコードの変更に
失敗した回数」を取り出す監視の式を組み立てられるかで検証する。実際の出力を採取し、
文書に載っていない系列がないこと、文書にあって出力にない系列がないことを突き合わせる。

**Acceptance Scenarios**:

1. **Given** 既定設定で起動し計測値を一度取得した状態、**When** 出力に現れる系列名を文書の記載と突き合わせる、**Then** すべての系列が記載されており、名前が文字列として一致する
2. **Given** 文書に記載されたある系列、**When** その項目を読む、**Then** 名前・種別・単位・意味・付与されるラベル・値が変化する契機がすべて記載されている
3. **Given** ラベルを持つ系列、**When** その記載を読む、**Then** ラベル名と取りうる値の候補が列挙されている
4. **Given** 外部 API がエラーを返した状況、**When** 文書のエラー分類を読む、**Then** そのエラーが再試行されるものか否かが判別できる
5. **Given** 文書を読んだ運用者、**When** 計測値に含まれない情報を確認する、**Then** ゾーン名・レコード名・レコード値・認証情報が含まれない旨と、その理由が記載されている

---

### User Story 3 - 文書が実装とずれていないと信じられる (Priority: P3)

運用者と保守担当者が、文書に書かれていることを**確かめずに信じられる**。
実装が変わったのに文書だけが取り残された状態が、気付かれずに続かない。

**Why this priority**: US1 と US2 が満たされても、時間が経てば文書は古くなる。
**古い文書は無い文書より悪い。** 読んだ人が誤った前提で操作する。ただし、
まず正しい文書が存在しなければこの性質は意味を持たないため、優先度は後になる。

**Independent Test**: 実装に設定項目または計測値を 1 つ追加し、文書を更新しないまま
品質ゲートを実行して失敗することを確認する。

**Acceptance Scenarios**:

1. **Given** 実装に計測値を 1 つ追加し文書を更新していない状態、**When** 品質ゲートを実行する、**Then** 失敗する
2. **Given** 実装に設定項目を 1 つ追加し文書を更新していない状態、**When** 品質ゲートを実行する、**Then** 失敗する
3. **Given** 文書に記載があって実装に存在しない項目がある状態、**When** 品質ゲートを実行する、**Then** 失敗する
4. **Given** 規範が要求しているが実装されていない機能がある、**When** 文書の該当箇所を読む、**Then** **未実装であることが明記されている**。要求されている姿を実装済みであるかのように書かない

---

### Edge Cases

- **公開形式で名前が変わる**: 計測値の名前に接尾辞が付く、分布が複数の系列に展開される
  場合、文書の名前が実際の出力と食い違う。**実際に出力される名前**を記載し、実装内部での
  呼び名をそのまま載せない。
- **まだ記録が発生していない系列**: 出力に現れない。突き合わせでは「未出現」を記載漏れと
  区別できる必要がある。
- **設定項目の意味がサービスごとに違う**: 同じ項目名が、あるサービスでは接続先 URL、
  別のサービスでは識別子を意味する。一覧の 1 行では表せない。
- **意図的に存在しない設定項目**: 「用意していない」ことに理由がある項目は、
  存在しないという事実だけでなく理由も記す。書かないと、次に読む人が「足りない」と
  判断して追加しうる。
- **規範と実装が食い違う**: 規範が MUST としている機能が未実装である場合がある。
  文書は**実装の事実**を書く。要求されている姿を書くと、読んだ人が動かない機能を
  前提に構成を組む。
- **実装が変わったのに文書だけ残る**: 機械的に検出できなければならない。文書の記述の
  すべてを機械検査できるわけではないため、**何を検査し何を検査しないか**が定まっている
  必要がある。
- **無認証で公開される内容の説明**: 計測値は無認証の経路で公開される。文書に実例を
  載せる場合も、そこに機微な値を含めない。
- **監視基盤が付与する情報**: 収集元の識別など、本サービスの出力ではない。文書の対象は
  本サービスが出力する内容に限る。

## Requirements *(mandatory)*

### Functional Requirements

#### 掲載範囲

- **FR-001**: 外部から観測・設定できる面を 1 つの文書にまとめて提供すること。対象は、設定項目、アクセストークンの供給元、公開する経路、計測値、ログ、追跡情報、エラーの分類、扱えるレコードの種別と制約、既知の制限とする。
- **FR-002**: `README.md` から文書への導線を設けること。
- **FR-003**: 記述は日本語とし、既存の利用者向け文書と同じ表記規則に従うこと。サービスの呼称は規範が定める表記に従うこと。

#### 設定項目 (US1)

- **FR-004**: 受け付けるすべての設定項目について、名前・既定値・意味を記載すること。
- **FR-005**: **意図的に用意していない設定項目**について、存在しないことと、その理由を記載すること。
- **FR-006**: 設定項目の組み合わせに関する規則 (排他、必須、条件付き必須) を記載すること。

#### アクセストークンの供給元 (US1)

- **FR-007**: 供給元ごとに、**識別子に何を渡すか**を記載すること。
- **FR-008**: 供給元ごとに、**シークレットのどの部分がトークンとして読まれるか**を記載すること。値全体が読まれるのか、値の中の特定のフィールドが読まれるのかを区別できること。
- **FR-009**: 値の中の特定のフィールドが読まれる供給元については、**そのフィールド名**と、それが設定で変更できるかどうかを記載すること。
- **FR-010**: 供給元ごとに、**何によって認証されるか**を記載すること。参照される環境変数、資格情報の解決順を含む。
- **FR-011**: 供給元ごとに、**必要な権限**を記載すること。
- **FR-012**: 同じ設定項目が供給元によって異なる意味を持つ場合、その違いを明示すること。
- **FR-013**: 供給元ごとに、トークンを格納する具体的な手順を記載すること。
- **FR-014**: 供給元をまたいで比較できる形を含めること。1 つを選ぶ際に、供給元ごとの節を順に読まなくても違いが分かること。
- **FR-015**: トークンの取得頻度と、外部で差し替えたときの反映のされ方を記載すること。

#### 計測値・ログ・追跡情報 (US2)

- **FR-016**: 公開するすべての系列について、**名前**・**種別**・**単位**・**意味**・**付与されるラベル**・**値が変化する契機**を記載すること。単位を持たない系列については、持たない旨が読み取れること。
- **FR-017**: 記載する名前は、実際の出力に現れる名前そのものであること。
- **FR-018**: ラベルを持つ系列については、ラベル名と、そのラベルが取りうる値の候補を列挙すること。
- **FR-019**: 分布として記録される系列については、公開形式で複数の系列に展開されることと、展開後の名前を示すこと。
- **FR-020**: 両形式 (Prometheus 形式と OpenTelemetry 形式) が同一の計測値を表す旨を記載すること。名前の見え方が異なる系列については、両方の名前を示すこと。
- **FR-021**: ゾーン名・レコード名・レコード値・認証情報が計測値に含まれない旨と、**その理由**を記載すること。
- **FR-022**: まだ記録が発生していない系列が出力に現れないことを注記すること。
- **FR-023**: 計測値がどの利用者操作・どの外部呼び出しに対応するかが読み取れること。
- **FR-024**: ログに出る内容と、外部 API のエラーがどう記録されるかを記載すること。
- **FR-025**: 追跡情報について、送出される条件と、要求 1 件がどう表現されるかを記載すること。

#### エラーとレコードの制約 (US2)

- **FR-026**: エラーの分類と、それが外部にどう見えるかの対応を記載すること。再試行されるものとされないものを判別できること。
- **FR-027**: 扱えるレコードの種別と、種別ごとの制約を記載すること。
- **FR-028**: 名前の表現がどう正規化されるかを記載すること。

#### 事実に忠実であること (US3)

- **FR-029**: 文書は**実装の事実**を記載すること。規範が要求していても実装されていない機能は、**未実装であることを明記すること**。実装済みであるかのように書かないこと。
- **FR-030**: 実装上の制限を「既知の制限」としてまとめて記載すること。個々の節に散らさず、1 か所で見渡せること。

#### 文書と実装の一致 (US3)

- **FR-031**: 文書の記載と実装の食い違いを**機械的に検出できること**。実装側に追加・削除・改名があった際、文書の更新漏れが品質ゲートで検出されること。
- **FR-032**: 機械的に検査する対象と、検査しない対象を定めること。文書のすべてを検査できるわけではないため、どこが自動で守られ、どこが人の注意に委ねられているかが分かること。
- **FR-033**: 検査は既存の品質ゲートの一部として実行されること。独立した手順にしないこと。実行を忘れられる経路を作らない。

### Key Entities

- **リファレンス項目**: 文書の記述単位。名前と、その項目に必要な属性の集合を持つ。属性は項目の種類によって異なる (計測値なら種別・単位・ラベル、設定項目なら既定値・意味)。
- **供給元**: アクセストークンの取得元。識別子の意味、トークンが読まれる位置、認証の手段、必要な権限を属性として持つ。
- **公開形式**: 計測値の見え方。同一の計測値に対して、形式ごとの名前を持つ。
- **既知の制限**: 実装されていない、または変更できない事項。規範が要求しているかどうかを属性として持つ。
- **検査対象**: 文書と実装の一致を機械的に確かめられる項目の集合。列挙できるものに限られる。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 実装コードを読んだことのない運用者が、文書だけを見て 4 つのシークレット管理サービスそれぞれにトークンを格納し、起動できる。
- **SC-002**: 供給元ごとに「識別子に渡すもの」「トークンが読まれる位置」「認証の手段」「必要な権限」の 4 項目に欠けがない。
- **SC-003**: 運用者は README を起点に、リンクを **1 回**たどるだけで文書に到達できる。
- **SC-004**: 実際に出力される系列のうち、文書に記載のないものが **0 件**である。また、文書に記載があって実装に存在しないものが **0 件**である。
- **SC-005**: 実際に受け付けられる設定項目のうち、文書に記載のないものが **0 件**である。また、文書に記載があって受け付けられないものが **0 件**である。
- **SC-006**: 文書に記載された全系列について、名前・種別・単位・意味・ラベル・値が変化する契機の 6 項目に欠けがない。
- **SC-007**: 実装コードを読んだことのない運用者が、文書だけを見て「DNS レコードの変更に失敗した回数」を取り出す監視の式を組み立てられる。
- **SC-008**: 実装に計測値または設定項目を 1 つ追加し、文書を更新しないまま品質ゲートを実行すると**失敗する**。
- **SC-009**: 規範が要求していて実装されていない機能のうち、文書がそれを実装済みであるかのように記述しているものが **0 件**である。

## Assumptions

### 掲載と表記

- 掲載先は `docs/` 配下の利用者向け文書とし、README からリンクする。README 本文に埋め込まないのは、README が既にデプロイ手順と利用前提条件で長く、参照用の表を足すと通読の妨げになるため。
- 記述言語は日本語とする。既存の README・`docs/development.md` と揃えるため。
- 対象は本サービスが定義する内容に限る。ExternalDNS 本体が出力する計測値、監視基盤が付与する情報、上流チャートの設定は対象外とする。ただし、上流と噛み合わない点 (待ち受け時間の既定値など) は既知の制限として触れる。

### 機械的な検査の範囲

- 検査するのは**列挙できるもの**に限る。設定項目の名前、計測値の名前とラベル、扱えるレコードの種別、公開する経路が該当する。
- 検査しないのは**散文**である。認証の解決順、必要な権限、格納手順、制限の説明は人が保つ。これらは実装から機械的に導けない。
- この非対称を文書に明記する。「検査されているから正しい」と読まれると、検査していない部分の誤りが見過ごされる。
- 検査は既存の品質ゲートに載せる。新たな検証基盤は作らない。

### 現在の状態

- 本仕様の US1 と US2 に相当する記述は、`docs/reference.md` として**すでに存在する** (コミット `98783eb`)。本仕様はそれを含めて機能全体を定義する。
- **US3 (機械的な検査) は未実装である。** 現状、文書と実装の一致は人の注意に委ねられている。

### 範囲外

- **実装の変更は行わない。** 文書を書く過程で、実際の出力名が実装内部の呼び名と異なる、あるいは規範が要求する機能が未実装であると判明した場合も、記載を事実に合わせることで対応する。
- 上記に該当する事項として、**ログの OpenTelemetry 形式での送出が未実装である**ことが判明している。規範 (原則 V) は MUST としているが、実装されていない。本機能では既知の制限として記載するに留め、**実装は別の機能として扱う**。
- 計測値の追加・改名・削除は行わない。ゾーンロックの取得・解放が計測されていないことも、既知の制限として記載するに留める。
