# Research: リファレンス文書

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-10

本書は Phase 0 の調査結果を記録する。US1・US2 に相当する記述は
`docs/reference.md` として既に存在するため、調査の対象は主に **US3
(文書と実装の一致を機械的に検出する)** である。

---

## R1. 文書と実装のどちらを正とするか

**Decision**: **文書を人が書き、実装から取り出した事実と突き合わせる。**
文書を実装から生成しない。

**Rationale**: 文書の価値の大半は散文にある。「Vault はシークレット内の `token`
フィールドを読む」「`--dpf-token-secret-endpoint` は GCP ではプロジェクト ID を
意味する」「AWS ではカスタマー管理の KMS キーを使う場合 `kms:Decrypt` が要る」——
これらは実装のコードから機械的に導けない。生成方式を採ると、生成できる部分と
手書きの部分が混在し、どちらを編集すればよいかが分からない文書になる。

突き合わせ方式なら、文書は 1 つの読み物のまま保たれ、**列挙できる事実だけ**が
検査される。検査の対象が狭いことは弱点ではなく、境界が明示されていることが
FR-032 の要求である。

**Alternatives considered**:

- **実装から文書を生成する**: 却下。散文を生成できない。生成部と手書き部の
  境界が文書の中に現れ、読み手にも書き手にも負担になる。
- **文書の内容を Go のコードとして持ち、両方から参照する**: 却下。更新すべき
  場所が「実装」「中間表現」「文書」の 3 か所になる。突き合わせ方式なら 2 か所で済む。
- **検査せず、レビューに委ねる**: 却下。SC-008 が「文書を更新しないまま品質ゲートを
  実行すると失敗する」を求めている。人の注意は時間とともに薄れる。

## R2. 文書のどこを検査対象と定めるか

**Decision**: 検査する表の直前に **HTML コメントの印**を置く。印のない記述は
検査しない。

```markdown
<!-- reference:flags -->
| フラグ | 既定 | 内容 |
|---|---|---|
| `--domain-filter` | (なし) | 管理対象ドメイン... |
```

**Rationale**: 印には 2 つの役目がある。

1. 検査する箇所を解析器に伝える。見出しの文字列や表の位置に依存すると、
   節を並べ替えただけで検査が壊れる、あるいは黙って何も検査しなくなる
2. **読み手に「ここは機械的に守られている」と伝える。** FR-032 が求める
   「何が検査され、何が検査されていないか」が、文書そのものの上に現れる

印がない箇所は人が保つ。この非対称を文書に明記する (FR-032)。「検査されて
いるから正しい」と読まれると、検査していない部分の誤りが見過ごされる。

**Alternatives considered**:

- **見出しで場所を特定する**: 却下。見出しの文言を変えただけで検査対象を
  見失う。しかも**黙って**見失う。
- **文書全体を走査して表を順に拾う**: 却下。表が増減するたびに添字がずれる。
  何を検査しているのかが文書からも解析器からも読めない。
- **別ファイルに検査対象を列挙する**: 却下。文書と一覧が離れ、文書だけを見て
  「ここは守られている」と分からない。

## R3. 印が消えた場合にどう振る舞うか

**Decision**: **印が見つからなければ検査を失敗させる。** 「対象がないので
何も検査しない」で通さない。

**Rationale**: 原則 VI (Default-Deny) がここに効く。検査の側が「見つからない
→ 何もしない → 成功」と振る舞うと、印を消すだけで検査を無効化できる。
文書の表ごと消しても気付けない。

期待する印の一覧を検査側に持たせ、**すべて揃っていることを先に確かめる**。
検査する組を減らすには、検査側のコードを変える必要がある。差分としてレビューに
現れる。

**Alternatives considered**:

- **印が無ければその組を飛ばす**: 却下。上記のとおり無効化が差分に現れない。
- **文書側に「検査対象の一覧」を書く**: 却下。文書を書き換えるだけで検査を
  緩められる。検査の設定は検査の側に置く。

## R4. 実装側の事実をどこから取り出すか

**Decision**: 組ごとに最も直接的な源を選ぶ。**製品コードを変更しない。**

| 検査する組 | 源 | 取り出し方 |
|---|---|---|
| 設定項目の名前と既定値 | `config.Usage()` | 公開関数。`--help` が出す文字列そのもの |
| シークレット管理サービスの名前 | `config.Load` | 各名前で読み込みを試し、受理されることを確かめる |
| 計測値の系列名 | Prometheus 形式の出力 | 各計測器に 1 件記録して収集し、現れた系列名を集める |
| `operation` ラベルの値 | `internal/dpf` の構文木 | `observe` に渡される文字列リテラル |
| レコード種別 | `provider.SupportedRecordTypes()` | 公開関数 |
| 公開する経路 | `internal/webhook` と `internal/server` の構文木 | `mux.Handle` / `mux.HandleFunc` に渡される文字列リテラル |

**Rationale**: 3 種類の取り出し方が混在するのは、事実の在り処が違うためである。

**公開関数がある場合はそれを使う** (設定項目、レコード種別)。最も壊れにくい。

**計測値は出力から採る。** FR-017 が「実際の出力に現れる名前そのもの」を求めて
いる。実装内部の計測器名は `dns_record_changes` だが、Prometheus 形式では
`_total` が付き、分布は `_bucket` `_sum` `_count` に展開される。内部の名前を
突き合わせても、文書の読者が見る名前を守れない。計測器に 1 件ずつ記録してから
収集すれば、未記録の系列が現れない問題 (FR-022) も同時に避けられる。

**構文木を読むのは、他に源がない場合に限る** (`operation` ラベル、経路)。
いずれも文字列リテラルとしてのみ存在し、実行時に列挙する手段がない。
公開する関数を足せば実行時に取れるが、それは製品コードの変更であり、
検査のために製品の面を広げることになる。構文木の読み取りは検査の側に閉じる。

**経路の検査には副次的な価値がある。** 原則 I が「独自のエンドポイントを
追加しない」を定めているが、これまで文書上の約束でしかなかった。経路を
突き合わせることで、**原則 I が機械的に守られる**ようになる。

**Alternatives considered**:

- **検査のために公開関数を足す** (`config.FlagNames()`、`webhook.Routes()` など):
  却下。製品の公開面を検査の都合で広げる。仕様が「実装の変更は行わない」を
  範囲外として明示している。
- **構文木ではなく文字列検索 (grep)**: 却下。コメントや文字列の中の似た記述を
  拾う。構文木なら呼び出しの引数だけを見られる。
- **計測器の名前を実装から直接読む**: 却下。上記のとおり出力名と一致しない。

## R5. 検査をどこで走らせるか

**Decision**: `test/docs/` に置き、`go test ./...` に載せる。既存の品質ゲート
(`make all` と CI) がそのまま実行する。

**Rationale**: FR-033 が「独立した手順にしない」を求めている。専用のスクリプトに
すると、実行を忘れられる経路ができる。

`test/` 配下に置くのは既存の構成に合わせるためである
(`test/contract`、`test/integration`、`test/e2e`)。外部への接続を要さないため、
`test/e2e` のような環境変数による読み飛ばしは設けない。**常に走る。**

**Alternatives considered**:

- **`internal/` の各パッケージに白箱テストとして分散させる**: 却下。文書を
  読む処理が複数のパッケージに重複する。また「文書との一致」という 1 つの
  関心事が散る。
- **Makefile の独立した目標にする**: 却下。`make all` に入れ忘れる、CI に
  入れ忘れるという経路ができる。`go test ./...` なら既に両方に載っている。
- **CI 専用のスクリプトにする**: 却下。手元で走らせられないと、書き手は
  push するまで結果を知れない。

## R6. 何を検査しないと定めるか

**Decision**: 次は検査しない。**文書にそう明記する。**

| 検査しないもの | 理由 |
|---|---|
| 認証の解決順 | 各 SDK の内部仕様であり、こちらのコードに現れない |
| 必要な権限 (IAM ポリシー等) | 外部サービスの仕様。こちらから確かめられない |
| シークレットへのトークンの格納手順 | 同上 |
| トークンが読まれる位置 (値全体か、特定のフィールドか) | 依存ライブラリの既定値であり、こちらのコードには「オプションを渡していない」ことしか現れない |
| エラーの分類 | 分類そのものは実装にあるが、外部 API の状態コードとの対応は網羅的に列挙できない |
| 既知の制限の説明 | 散文 |
| 制約の内容 (TTL の範囲、CNAME の排他など) | 検証ロジックの単体テストが守っている。文書との文字列一致には意味がない |

**Rationale**: 検査できないものを検査できるように見せない。文書に
「ここは人が保っている」と書くことが、読み手にとっても書き手にとっても
正直である。

**トークンが読まれる位置を検査できないのは痛い。** 本機能の発端になった
指摘 (「どの key になるかが書いてない」) の中心であり、誤ると認証に失敗する。
しかしこれは依存ライブラリの既定値であり、こちらのコードには現れない。
ライブラリが既定を変えれば文書は黙って誤りになる。

緩和として、**依存ライブラリの版を固定する**方針が既にある (原則: バージョン
固定)。版が上がるときは Pull Request として現れ、そこで確かめられる。
この関係を文書に注記する。

**Alternatives considered**:

- **実際のシークレット管理サービスに接続して確かめる**: 却下。4 つのサービスの
  資格情報を CI に持ち込むことになる。得られる保証に対して代償が大きすぎる。
- **依存ライブラリの構文木を読んで既定値を取り出す**: 却下。他所のコードの
  内部構造に依存する検査は、相手の実装変更で壊れる。壊れ方が「誤検知」なら
  まだよいが、「見逃し」になりうる。
