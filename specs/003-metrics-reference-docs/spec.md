# Feature Specification: メトリクスのリファレンス文書

**Feature Branch**: `003-metrics-reference-docs`

**Created**: 2026-09-09

**Status**: Draft

**Input**: User description: "/metricsが提供するメトリクスの名前、種類、内容をREADME.mdから辿れるところにドキュメント化してください。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - スクレイプした値の意味を知る (Priority: P1)

本サービスを導入した運用者が、監視基盤で `/metrics` を収集し始めた。集まってきた系列が
何を数えているのか分からない。README を開き、可観測性の記述から一覧へたどり着き、
系列名ごとに「何を数えた値か」「増えるのはどんなときか」を確認できる。

**Why this priority**: これができないと、収集はできても値を読めない。メトリクスを
提供している意味が運用者に届かない。他のどのストーリーもこの一覧の存在を前提とする。

**Independent Test**: README だけを起点に、本サービスの実装コードを読まずに、
`/metrics` に現れる全系列の意味を説明できるかで検証できる。実際の出力を採取し、
一覧に載っていない系列がないこと、一覧にあって出力にない系列がないことを突き合わせる。

**Acceptance Scenarios**:

1. **Given** 本サービスを既定設定で起動し `/metrics` を一度取得した状態、
   **When** 出力に現れる系列名を一覧の記載と突き合わせる、
   **Then** すべての系列が一覧に記載されており、記載された名前が出力の名前と文字列として一致する
2. **Given** README を開いた運用者、
   **When** 可観測性に関する記述をたどる、
   **Then** メトリクス一覧への導線があり、そこから一覧に到達できる
3. **Given** 一覧に記載されたある系列、
   **When** その項目を読む、
   **Then** 名前・種別・単位・意味・付与されるラベル・値が変化する契機がすべて記載されている

---

### User Story 2 - アラートとダッシュボードを設計する (Priority: P2)

監視の担当者が、DNS 更新の失敗を検知するアラートを作ろうとしている。どの系列の
どのラベルで絞り込めば「失敗」だけを取り出せるのかを、一覧から判断できる。

**Why this priority**: 意味が分かる (P1) だけでは式が書けない。種別 (累積か分布か) と
ラベルの取りうる値が分からないと、絞り込みも増分の取り方も決められない。ただし
P1 がなければこのストーリー自体が成立しないため P2 とする。

**Independent Test**: 一覧の記載だけを頼りに「変更の適用が失敗した件数」「DPF API の
呼び出しのうち失敗した割合」を求める式を組み立てられるかで検証できる。

**Acceptance Scenarios**:

1. **Given** ラベルを持つ系列の項目、
   **When** その記載を読む、
   **Then** ラベル名と、そのラベルが取りうる値の候補が列挙されている
2. **Given** 分布として記録される系列の項目、
   **When** その記載を読む、
   **Then** 分布であることと単位が明示されている
3. **Given** まだ一度も記録が発生していない起動直後の状態、
   **When** `/metrics` を取得する、
   **Then** 未出現の系列がありうる旨が一覧に注記されており、運用者はそれを欠落と誤解しない

---

### User Story 3 - OTLP で受け取った値と対応づける (Priority: P3)

OTLP でメトリクスを収集している利用者が、受け取った計測値が `/metrics` の
どの系列に対応するのかを確認する。

**Why this priority**: 本サービスは 2 形式で同一の計測値を提供する。形式によって
名前の見え方が変わるため、対応が分からないと同じ値を別物として扱ってしまう。
ただし片方の形式だけを使う利用者には不要であり、優先度は下げる。

**Independent Test**: OTLP で受け取った計測値の名前から、一覧を引いて対応する
`/metrics` の系列名を特定できるかで検証できる。

**Acceptance Scenarios**:

1. **Given** 2 形式で名前の見え方が異なる系列、
   **When** 一覧の該当項目を読む、
   **Then** 両形式それぞれでの名前が示されている
2. **Given** 一覧の冒頭、
   **When** それを読む、
   **Then** 両形式が同一の計測値を表すことが明示されている

---

### Edge Cases

- 公開形式への変換で名前に接尾辞が付く、または分布が複数の系列に展開される場合、
  一覧に書かれた名前が実際の出力と食い違う。一覧は**実際に出力される名前**を記載し、
  実装内部での呼び名をそのまま載せない。
- まだ一度も記録が発生していない系列は出力に現れない。一覧との突き合わせでは、
  この「未出現」を記載漏れと区別できる必要がある。
- 実装にメトリクスが追加・削除・改名されたとき、一覧だけが取り残される。
  食い違いは機械的に検出できなければならない。
- 一覧は無認証で公開される `/metrics` の内容を説明する文書である。ゾーン名・
  レコード名・レコード値・認証情報が系列やラベルに現れない旨を明示し、
  実例を載せる場合もそれらを含めない。
- 監視基盤側が付与するラベル (収集元の識別など) は本サービスの出力ではない。
  一覧の対象は本サービスが出力する内容に限る。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `/metrics` が公開するすべての系列について、その一覧を利用者向け文書として
  提供すること。
- **FR-002**: 一覧の各項目は、**名前**・**種別**・**単位**・**意味**・**付与されるラベル**・
  **値が変化する契機**を含むこと。単位を持たない系列については、単位を持たない旨が
  読み取れること。
- **FR-003**: 記載する名前は、`/metrics` の出力に現れる名前そのものであること。
- **FR-004**: ラベルを持つ系列については、ラベル名と、そのラベルが取りうる値の候補を
  列挙すること。
- **FR-005**: 分布として記録される系列については、公開形式でそれが複数の系列に
  展開されることと、展開後の系列名を示すこと。
- **FR-006**: `README.md` から一覧への導線を設けること。README の可観測性に関する
  記述から到達できること。
- **FR-007**: 一覧から、そのメトリクスがどの利用者操作・どの外部呼び出しに対応するかが
  読み取れること。利用者が観測結果を自分の操作に結び付けられるようにするため。
- **FR-008**: 一覧に、両形式 (Prometheus 形式と OpenTelemetry 形式) が同一の計測値を
  表す旨を記載すること。両形式で名前の見え方が異なる系列については、両方の名前を示すこと。
- **FR-009**: 一覧に、ゾーン名・レコード名・レコード値・認証情報がメトリクスに
  含まれない旨を記載すること。
- **FR-010**: 一覧に記載された系列と、実際に `/metrics` が出力する系列の食い違いを
  機械的に検出できること。実装側にメトリクスを追加・削除・改名した際、一覧の更新漏れが
  品質ゲートで検出されること。
- **FR-011**: 一覧の記述は日本語とし、既存の利用者向け文書と同じ表記規則に従うこと。
  サービスの呼称は constitution が定める表記に従うこと。
- **FR-012**: まだ記録が発生していない系列が `/metrics` に現れないことを一覧に注記すること。

### Key Entities

- **メトリクス項目**: 一覧の 1 行に対応する記述単位。名前、種別、単位、意味、
  ラベルの集合、値が変化する契機を属性として持つ。
- **ラベル**: メトリクス項目に付随する識別子。ラベル名と、取りうる値の候補の集合を持つ。
- **公開形式**: 計測値の見え方。Prometheus 形式と OpenTelemetry 形式の 2 つがあり、
  同一の計測値に対してそれぞれの名前を持つ。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 運用者は README を起点に、リンクを 1 回たどるだけでメトリクス一覧に
  到達できる。
- **SC-002**: `/metrics` が出力する系列のうち、一覧に記載のないものが 0 件である。
  また、一覧に記載があって実装に存在しないものが 0 件である。
- **SC-003**: 一覧に記載された全項目について、名前・種別・単位・意味・ラベル・
  値が変化する契機の 6 項目に欠けがない。
- **SC-004**: 本サービスの実装コードを読んだことのない運用者が、一覧だけを見て
  「DNS レコードの変更に失敗した回数」を取り出す監視の式を組み立てられる。
- **SC-005**: 実装にメトリクスを 1 つ追加し、一覧を更新しないまま品質ゲートを実行すると
  失敗する。

## Assumptions

- 掲載先は `docs/` 配下の新規の利用者向け文書とし、README の「可観測性」節から
  リンクする。README 本文に一覧を直接埋め込まないのは、README が既にデプロイ手順と
  利用前提条件で長く、参照用の表を足すと通読の妨げになるため。既存の
  `docs/development.md` と同じ配置規則に従う。
- 対象は本サービスが定義するメトリクスに限る。ExternalDNS 本体が出力するメトリクス、
  および監視基盤が付与する情報は対象外とする。
- 記述言語は日本語とする。既存の README・`docs/development.md` と揃えるため。
- 一覧と実装の一致検証は、既存の CI 品質ゲートの一部として実行されることを前提とする。
  新たな検証基盤の構築は本機能の範囲外とする。
- 本機能は文書とその検証のみを対象とし、メトリクスの追加・改名・削除は行わない。
  一覧を書く過程で実際の出力名が実装内部の呼び名と異なると判明した場合も、
  記載を実際の出力に合わせることで対応し、実装は変更しない。
