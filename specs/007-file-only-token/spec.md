# Feature Specification: アクセストークンの供給元をファイルに限る

**Feature Branch**: `feature/007-file-only-token`

**Created**: 2026-10-06

**Status**: Draft

**Input**: User description: "TOKEN取得に関してですが、このプログラムはk8s上でしか動作しないため、key managerから直接tokenをうけとる機能は廃止します。token取得はfileベースのみとします。"

## User Scenarios & Testing *(mandatory)*

本機能の利用者は **本 provider を Kubernetes 上にデプロイする運用者** である。
IIJ DNSプラットフォームサービス (DPF) のアクセストークンを用意し、ExternalDNS のサイドカーとして本 provider に渡す。

現状、トークンの供給元は「マウントされたファイル」と「外部のシークレット管理
サービス (Vault / AWS / Azure / GCP)」の 2 系統ある。本 provider は Kubernetes 上で
しか動作しない。Kubernetes には、外部のシークレット管理サービスの値を Secret や
ボリュームとして Pod へ届ける仕組みがすでにある。**本 provider 自身が各サービスへ
接続する経路は、その仕組みと重複している。** 本機能はこの経路を廃止し、
供給元をファイルの 1 系統に限る。

### User Story 1 - トークンをファイルだけで与える (Priority: P1)

運用者は、トークンを収めたファイルのパスを 1 つ指定して本 provider を起動する。
指定の仕方はこれしかない。どの供給元を選ぶか、供給元ごとに何を設定するかを
考える必要がない。トークンを差し替えれば、再起動なしに次の要求から使われる。

**Why this priority**: 本機能の中心である。これが成立しなければトークンを
与える手段がなくなる。

**Independent Test**: 検証用の Kubernetes 環境で、トークンを収めた Secret を
マウントし、そのパスを指定して本 provider を起動する。レコードの取得と適用が
成功することを確認する。続いて Secret の内容を別の有効なトークンへ差し替え、
再起動せずに次の要求が新しいトークンで成功することを確認する。

**Acceptance Scenarios**:

1. **Given** トークンを収めたファイルがある、**When** そのパスを指定して起動する、
   **Then** 本 provider は起動し、DPF への要求がそのトークンで成功する
2. **Given** 起動中である、**When** ファイルの内容を別の有効なトークンへ差し替える、
   **Then** 再起動なしに、次の要求から新しいトークンが使われる
3. **Given** トークンのファイルを指定していない、**When** 起動する、
   **Then** 起動に失敗し、ファイルの指定が必要である旨が示される
4. **Given** 指定したファイルが存在しない、または読めない、**When** DPF への要求が
   発生する、**Then** その要求は恒久的な失敗となり、メッセージにトークンの値や
   ファイルの内容を含まない

---

### User Story 2 - 廃止した設定を誤って残したまま起動しない (Priority: P2)

運用者が古い設定例や手元のメモを元に、シークレット管理サービス用の設定を指定した
とする。本 provider はそれを黙って無視せず、起動を中止する。運用者は、自分の
設定が意図どおりに解釈されていないことを、起動の時点で知る。

**Why this priority**: 黙って無視すると、運用者はシークレット管理サービスから
トークンを取っているつもりで、実際には別の経路に依存することになる。
原則 VI (想定外の値を受け取ったら起動を中止する) の適用である。

**Independent Test**: シークレット管理サービス用の設定を含めて起動し、起動に
失敗すること、どの設定が受け付けられなかったかがメッセージから分かることを
確認する。ファイルの指定と併用した場合も同様に確認する。

**Acceptance Scenarios**:

1. **Given** シークレット管理サービス用の設定 (サービスの種類、識別子、接続先の
   いずれか) を指定した、**When** 起動する、**Then** 起動に失敗し、受け付けられ
   なかった設定の名前がメッセージに含まれる
2. **Given** トークンのファイルとシークレット管理サービス用の設定を併せて指定した、
   **When** 起動する、**Then** ファイルの指定があっても起動に失敗する
3. **Given** シークレット管理サービスへの接続に使われていた環境変数
   (例: `VAULT_TOKEN`、`AWS_REGION`) が Pod に設定されている、**When** 起動する、
   **Then** 本 provider はそれらを参照せず、トークンの取得はファイルからのみ行う

---

### User Story 3 - 外部のシークレット管理サービスの値を使い続ける (Priority: P3)

これまでシークレット管理サービスにトークンを置いていた運用者は、その保管場所を
変えずに済ませたい。運用者は Kubernetes 側の仕組みでトークンを Pod 内のファイルとして
届け、本 provider にはそのパスを指定する。README から、その構成への道筋が分かる。

**Why this priority**: 本機能によって失われる使い方の受け皿である。ただし本 provider
自身の機能ではなく、文書による案内であるため P3 とする。

**Independent Test**: README とリファレンス文書を読み、シークレット管理サービスに
置いたトークンをファイルとして届ける構成へ、本 provider 以外の文書を参照しつつ
到達できることを確認する。

**Acceptance Scenarios**:

1. **Given** トークンを外部のシークレット管理サービスに置いている、**When** 運用者が
   README を読む、**Then** そのトークンを Kubernetes 側でファイルとして届け、
   `--dpf-token-file` で指定する構成が案内されている
2. **Given** 上記の構成で運用している、**When** シークレット管理サービス上で
   トークンをローテーションする、**Then** ファイルへの反映後、再起動なしに新しい
   トークンが使われる (反映までの遅延は Kubernetes 側の仕組みに依存する旨が
   文書に記されている)

---

### Edge Cases

- **Secret を `subPath` でマウントした場合**、Kubernetes は Secret の更新をその
  ファイルに反映しない。ローテーションが届かず、古いトークンが使われ続ける。
  本 provider はこれを検出できないため、文書で `subPath` を使わないよう注意する
- Secret の更新がファイルに届くまでには Kubernetes 側の遅延がある。その間は
  古いトークンが使われる。本 provider はこの遅延を短縮しない
- ファイルが空、または空白だけの場合はトークンの取得失敗として扱う (恒久的な失敗)
- ファイルの内容は全体を 1 つのトークンとして扱い、JSON 等として解釈しない
  (現行の振る舞いを維持する)
- シークレット管理サービスへの egress を許可した NetworkPolicy が残っていても、
  本 provider はそこへ接続しない。不要になった許可の削除は運用者の作業である
- 本 provider はまだタグ付きリリースを行っていない。したがって、廃止する経路を
  リリース版で利用している利用者はいない (Assumptions 参照)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、DPF のアクセストークンを**マウントされたファイルからのみ**
  取得しなければならない。他の供給元を持ってはならない
- **FR-002**: システムは、外部のシークレット管理サービスへ接続してはならない。
  トークンの取得以外の目的でも接続しない
- **FR-003**: システムは、トークンのファイルが指定されていない場合、起動を中止
  しなければならない
- **FR-004**: システムは、シークレット管理サービス用の設定
  (`--dpf-token-secret-manager`、`--dpf-token-secret-id`、
  `--dpf-token-secret-endpoint`) を受け付けてはならない。指定された場合は
  起動を中止し、受け付けなかった設定の名前を示さなければならない。
  黙って無視してはならない
- **FR-005**: システムは、シークレット管理サービスへの接続のために参照していた
  環境変数を、トークンの取得に用いてはならない
- **FR-006**: ファイルからの取得は、現行の振る舞いを保たなければならない。
  - DPF API を呼ぶたびにファイルを読み直す (キャッシュしない)
  - 内容が差し替えられれば、再起動なしに次の要求から反映する
  - 前後の空白を取り除く
  - 取得の失敗を恒久的な失敗として扱う
  - 失敗時のメッセージにトークンの値・ファイルの内容を含めない
- **FR-007**: 配布するコンテナイメージは、シークレット管理サービスへ接続する
  機能を含んではならない。廃止した経路のためだけに必要だった依存は、
  配布物から取り除かれなければならない
- **FR-008**: README とリファレンス文書は、トークンの供給元がファイルのみである
  ことを示さなければならない。シークレット管理サービス用の設定・認証方法・
  権限の説明を残してはならない
- **FR-009**: README は、外部のシークレット管理サービスに置いたトークンを
  Kubernetes 側の仕組みでファイルとして届ける構成を案内しなければならない。
  あわせて、`subPath` でマウントするとローテーションが届かないことを
  注意しなければならない
- **FR-010**: README が示す推奨 values と NetworkPolicy の例は、シークレット
  管理サービスへの egress を含んではならない

### Key Entities

- **トークンファイル**: DPF のアクセストークンを内容全体として収めたファイル。
  Kubernetes の Secret のマウント、または外部のシークレット管理サービスの値を
  ファイルとして届ける仕組みによって Pod 内に置かれる。本 provider が知るのは
  そのパスだけである

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: トークンの供給元を指定する設定項目が 1 つ (ファイルのパス) だけになる
- **SC-002**: 廃止した 3 つの設定のいずれを指定しても、起動が 100% 失敗する
- **SC-003**: 動作中の本 provider から、DPF API・名前解決・(設定した場合の)
  テレメトリの送出先以外への接続が 0 件である
- **SC-004**: 配布するイメージに含まれる依存モジュールの数が、本機能の前より減る。
  シークレット管理サービスのクライアントに由来する依存が 0 件になる
- **SC-005**: ファイル経由のトークンのローテーションが、再起動なしに反映される
  (既存の検証が引き続き成功する)
- **SC-006**: README とリファレンス文書に、シークレット管理サービスへの直接接続を
  前提とした記述が 0 件である

## Assumptions

- **本 provider は Kubernetes 上でのみ動作する。** Kubernetes 以外の環境での
  実行は想定しない
- 外部のシークレット管理サービスの値をファイルとして Pod へ届けることは、
  Kubernetes 側の仕組み (Secrets Store CSI Driver、External Secrets Operator 等) で
  実現できる。これらの導入と運用は本 provider の範囲外であり、README では
  構成の考え方を案内するにとどめる
- **本 provider はまだタグ付きリリースを行っていない。** 廃止する経路にリリース版で
  依存している利用者はいないため、移行期間 (非推奨の警告を出しつつ受け付ける期間) は
  設けず、即時に廃止する
- 現行の README は、シークレット管理サービスを使うより Secrets Store CSI Driver で
  ファイルを配置する方が露出が小さいと述べている (Vault の認証トークンを環境変数で
  渡す必要があるため)。本機能はこの推奨を唯一の経路に格上げするものである
- ファイルからの取得の振る舞い (FR-006) は 001 で定めたものであり、本機能では
  変えない

## Dependencies

- **constitution の改訂 (先行が必要)**: 現行の constitution は、トークンを
  「マウントされたファイル、または外部のシークレット管理サービス」から取得する
  ことを MUST としている (技術・配布制約 > セキュリティ: バイナリの既定拒否)。
  認証情報の受け取り経路 (コンテナイメージとチャートの既定拒否) と、
  シークレット管理サービスへの egress の扱いにも同じ前提がある。本機能はこれらと
  矛盾するため、**plan に進む前に constitution を改訂する必要がある**。
  → v3.0.0 (2026-10-06) で改訂済み
- **001 のトークン取得経路**: 本機能は 001 が定めた 2 系統のうち 1 系統を廃止する。
  001 の spec と、それに基づく 003 のリファレンス文書の記述が影響を受ける
- **e2e 検証**: 現行の e2e はトークンをファイル経由でのみ与えており、
  シークレット管理サービス経由の検証はない。ローテーションの検証 (SC-005) は
  そのまま使える
- **文書と実装の一致検査**: リファレンス文書のシークレット管理サービスの一覧は、
  実装と突き合わせて検査されている。一覧を削除する際は、検査も合わせて改める
  必要がある

## 背景: なぜ廃止するのか

シークレット管理サービスへの直接接続は、4 つのサービスそれぞれについて、
鍵の位置、認証方法、必要な権限、`--dpf-token-secret-endpoint` の意味が異なる。
運用者はサービスごとの違いを理解して設定しなければならず、本 provider は
4 つのクライアントを依存として抱え、その脆弱性とライセンスに追随し続ける
必要がある。

Kubernetes には、外部のシークレット管理サービスの値を Pod へ届ける汎用の仕組みが
すでにある。本 provider は Kubernetes 上でしか動かないので、その仕組みに任せれば
よい。本 provider はファイルを読むことだけに責任を持つ。

あわせて、Vault を使う場合は Vault の認証トークンを環境変数で渡す必要があった。
これは DPF のトークンを環境変数から受け取らないとした理由 (読み取られやすい) と
同じ問題を、別のトークンで抱えていたことになる。ファイルに限ることで、この
矛盾も解消する。
