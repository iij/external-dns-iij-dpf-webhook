# Phase 0 Research: ゾーン反映の実行者を DPF の記録に残す

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-15

調査対象は `github.com/iij/dpf-go` v0.1.0 の生成型と API 面である。

---

## R1. 記録を載せる場所

**Decision**: 一括更新 (`atomic_changes`) の要求に添える `description` に載せる。

`dpf-go` には `description` を持つ要求が 2 つある。

| 要求 | 用途 | 本サービスでの使用 |
|---|---|---|
| `PatchZoneAtomicChanges` | レコードの一括更新と反映を原子的に行う | **使用中** (001 research R3) |
| `PatchZoneCommit` | 編集済みの内容を反映する (非原子) | 使用しない |

本サービスは 001 で原子的な経路を選んでおり、反映は `atomic_changes` の一部として
行われる。**別の API 呼び出しは増えない。** 記録は反映と同じ要求に載る。

**Rationale**: 呼び出しを増やさないため、新しい失敗経路が生まれない。記録だけが
残って反映が失敗する、あるいはその逆も起こらない (spec の Edge Cases)。

**Alternatives considered**:

- *`PatchZoneCommit` を別に呼ぶ*: 却下。原子的な経路を捨てることになり、001 の
  FR-011 (反映完了前に成功を返さない) と FR-012 (部分成功を成功としない) の
  担保が崩れる

## R2. 記録は履歴として読み戻せる

**Decision**: `ZoneHistoriesAPI.GetZoneHistoryList` で読み戻し、**機械的に検証する。**

```go
type ZoneHistory struct {
	Id          int64          `json:"id"`
	CommittedAt time.Time      `json:"committed_at"`
	Description string         `json:"description"` // コメント
	Operator    NullableString `json:"operator"`    // 編集者
}
```

`GetZoneHistoryList(ctx, zoneId)` が `GetZoneHistories{Results []ZoneHistory}` を返す。
エンドポイントは `GET /zones/{ZoneId}/zone_histories` で、**「ゾーン反映履歴の一覧取得」**
と定義されている。本機能が記録するのはまさにこの「ゾーン反映」の履歴である。

**説明で絞り込める。** 問い合わせパラメータに `KeywordsDescription` があり、
説明に含まれる語で履歴を検索できる。検証は「全件を取って走査する」ではなく
「本サービスの記録を持つ履歴を引く」という形で書ける。

**この発見は受け入れ確認の形を変える。** 「DPF コンソールを人が開いて目で見る」
しかないと思っていたが、履歴は API から取れる。実環境での検証 (constitution v2.1.0)
で、適用した直後に履歴を読み、記録が付いていることを表明できる。

**Rationale**: 人手の確認に頼る受け入れ条件は、CI で守れない。守れない条件は
いずれ守られなくなる。

### 並び順の既定は昇順である (2026-09-15 実環境で判明)

`SearchOrder` の宣言は `default: "ASC"`、enum は `["ASC", "DESC"]` である。
**既定は最古から並ぶ。**

初版の実装はこれを確かめず「新しい順に返る」と決めつけ、`Limit(20)` だけを
指定した。結果、**ゾーン作成時の最古の履歴 20 件が毎回返り、新しい反映には
永久に届かなかった。** 実環境で `description="Zone Initialize"`
(`committed_at=2026-07-22`) が「最新」として返り、初めて気付いた。

既定に頼らず `Order(DESC)` を明示する。

### 取得は打ち切られた窓である

`Limit` で絞ると、履歴がその件数を超えるゾーンでは**窓が常に同じ件数で埋まる。**
新しい反映が増えても件数は変わらず、古い側が押し出される。

したがって次の 2 つを守る。

- **件数の増減で新しい反映の有無を判断しない。** 降順の先頭を見る
- **既存の履歴の不変を位置で比べない。** ID で突き合わせ、窓に残っているものだけを
  検査する。位置で比べると、押し出された分だけずれて別の履歴同士を比べる

## R3. `operator` があるのに `description` が要る理由

**Decision**: `description` に記録する。`operator` では足りない。

`ZoneHistory` は `Operator` (編集者) を持つ。これは DPF が資格情報から決める値で
あり、**本サービスが設定するものではない。**

区別できるのは「どの DPF アカウントが操作したか」までである。本サービス専用の
アカウントを与えている場合は実行者の判別に使えるが、次の場合には使えない。

- 人が DPF コンソールで使うアカウントと、本サービスに与えたアカウントが同じ
- 複数の自動化が同じアカウントを共有している

**どのソフトウェアが実行したか**は、そのソフトウェア自身が名乗るしかない。
`description` はそのための場所である。

**Rationale**: spec の狙いは「本 provider による反映と人手による反映を見分ける」
(SC-001) ことであり、アカウントの区別ではない。運用のアカウント設計に依存しない
方法でなければ、SC-001 は環境によって成り立たなくなる。

## R4. 記録する内容

**Decision**: 固定文字列 `external-dns-iij-dpf-webhook` のみとする。

spec の Assumptions が版番号・変更件数・対象レコード名を範囲外としている。
加えて、**版を入れるには新しい仕組みが要る。**

現状、版の概念はコンテナイメージの OCI ラベル (`org.opencontainers.image.version`)
にしかなく、ビルド引数として与えられる。バイナリの中には無い。記録に版を含めるには
`-ldflags` で変数を埋め込む仕組みを新設することになり、本機能の範囲を超える。

**Alternatives considered**:

- *変更件数を添える (`... created=3 updated=1 deleted=0`)*: 却下 (範囲外)。
  ログには既に同じ情報がある (001 FR-020)。履歴とログは `committed_at` で
  突き合わせられる
- *ゾーン名やレコード名を添える*: 却下。DPF の履歴は既にゾーンに紐づいており、
  変更内容は履歴本文 (`GetZoneHistoryText`) から取れる。重複する

## R5. 長さの制約は 80 オクテット (スキーマに宣言がある)

**Decision**: 上限は **80 オクテット**。固定文字列 28 オクテットで運用する。

典拠は `dpf-go` に同梱される OpenAPI 定義 (`openapi.json`) である。
`description` は共通スキーマ `Description` を参照する。

```json
"Description": {
  "type": "string",
  "description": "コメント",
  "default": "",
  "minLength": 0,
  "maxLength": 80
}
```

`PatchZoneAtomicChanges`・`PatchZoneCommit`・`ZoneHistory` の `description` は
いずれもこの同じスキーマを参照する。**送る側と読み戻す側で同じ制約が効く。**

| 項目 | 値 |
|---|---|
| 上限 | 80 オクテット |
| `external-dns-iij-dpf-webhook` | 28 オクテット |
| 余り | 52 オクテット |

`default` が `""` であるため、説明を省いた場合は空文字列になる。**本機能より前に
本サービスが行った反映は、履歴上で説明が空である。** これが人手の反映と区別できない
現状そのものである。

**Rationale**: 上限が宣言されているため、固定文字列が収まることは投げる前に
確かめられる。FR-006 (上限を超える場合に識別名を失わない) は、28 < 80 が定数として
成り立つことで満たされる。

**将来内容を増やす場合**: 52 オクテットの余りがある。版番号 (`v1.2.3` で 6〜7)
程度なら収まるが、**80 を超えないことを型または検査で保証しなければならない。**
可変長の内容を上限の確認なしに足さないこと。

**初版の誤り (2026-09-15 訂正)**: 当初この節は「制約は確認できなかった」「DPF の
スキーマは長さを宣言していない」と記し、001 の `TXT` と同じ未宣言の制約として
扱っていた。**誤りである。** 生成された Go の型が長さ検証を持たないことを、
スキーマに宣言がないことと混同した。`openapi.json` を読めば宣言されている。
`TXT` の `value` と違い、ここには投げる前に確かめる手段がある。

## R6. 境界のどちら側に置くか

**Decision**: `internal/dpf` の内側に置く。`Backend` インタフェースを変えない。

`description` は DPF の要求が持つ項目であり、原則 II が「境界の内側に留める」と
定めるトランスポートの詳細にあたる。上位層へ持ち出すと、`provider.Backend` の
`Apply` に DPF 固有の引数が増える。

記録する内容は固定文字列であり (R4)、呼び出しごとに変わらない。上位層から
渡す必要がない。

**Alternatives considered**:

- *`provider` 層が記録の内容を決めて境界越しに渡す*: 却下。`Apply` の署名に
  DPF 固有の概念が現れ、原則 II に反する。内容が固定である以上、渡す意味もない
- *記録の有無を設定で切り替えられるようにする*: 却下。設定項目を増やすだけの
  価値がない。記録しない理由が思いつかず、既定拒否 (原則 VI) の対象でもない
  (外部への到達性も権限も増やさない)

**検証の置き場所**: 固定文字列が要求に載ることは `internal/dpf` の単体テストで
固定する。履歴に現れることは実環境の検証で確かめる (R2)。
