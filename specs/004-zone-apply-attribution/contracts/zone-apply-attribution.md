# Contract: 反映の記録

**Feature**: [../spec.md](../spec.md) | **Date**: 2026-09-15

本機能は **001 の `contracts/dpf-client.md` に項目を 1 つ加える**ものである。
新しい境界も、新しいインタフェースも作らない。

---

## `Backend` インタフェースは変えない

`provider.Backend` の `Apply(ctx, zone, changes)` に引数を加えない (MUST NOT)。

記録する内容は固定文字列であり、呼び出しごとに変わらない。上位層から渡す理由が
ない。渡す設計にすると、DPF の要求が持つ項目という**トランスポートの詳細が
境界を越える**ことになり、原則 II に反する (research R6)。

上位層 (`internal/provider`、`internal/webhook`) は本機能の存在を知らない。

---

## 変更の適用に加わる要件

001 の `contracts/dpf-client.md` 「変更の適用」に次を加える。

- 一括更新の要求に、**実行者が本サービスであることを示す説明を添える (MUST)**。
  値は `external-dns-iij-dpf-webhook` とする (FR-002)
- 説明を**呼び出しごとに変えない (MUST NOT)**。変更セットの内容、ゾーン、時刻の
  いずれにも依存させない
- 説明を **80 オクテット以内に収める (MUST)**。DPF の共通スキーマ `Description` が
  `maxLength: 80` を宣言している (research R5)。固定文字列 28 オクテットでは定数と
  して成り立つが、可変長の内容を足す場合は型または検査で保証すること
- 説明の付与のために**追加の API 呼び出しを行わない (MUST NOT)**。反映と同じ
  要求に載せる。呼び出しを増やすと、記録だけが残って反映が失敗する経路が生まれる
- 説明を**レコードのコメントに書かない (MUST NOT)**。レコード単位のコメントは
  001 の逐語コピーの対象であり、本機能は触れない (FR-007)

**変わらないこと**: `overwrite_soa` と `overwrite_zone_apex_ns` を常に `false` で
送ること、管理対象外のレコードを逐語的にコピーすること、投入前ガード、反映完了まで
成功を返さないこと。本機能はこれらのいずれにも影響しない。

---

## 履歴の読み取り (検証にのみ用いる)

受け入れ確認のために、ゾーンの履歴を読む操作を境界の内側に用意する。

```
指定ゾーンの反映履歴を、新しい順に取得する
```

- 返すのは、反映時刻と説明の対
- **本サービスの通常の動作経路では使わない (MUST NOT)**。記録は運用者が読むため
  のものであり、本サービスがこれを読み返して動作を変えることはない
  (spec の Assumptions)
- 生成型を境界の外へ出さない。原則 II はこの操作にも等しく適用される

**なぜ実装するか**: 記録が実際に履歴へ現れることを、人の目視ではなく機械的に
確かめるため (research R2)。**人手の確認に頼る受け入れ条件は CI で守れず、
守れない条件はいずれ守られなくなる。**

---

## エラーの扱い

説明の付与は新しい失敗経路を作らない。反映と同じ要求に載るため、失敗すれば
それは反映の失敗である。001 の分類 (一時的 / 恒久的) がそのまま適用される。

**説明が原因で拒否された場合は恒久的な失敗になる。** 固定文字列であるため、
再試行しても結果は変わらない。この場合は本サービスの不具合であり、実環境の
検証で検出すべきものである (quickstart 2)。

SC-005 (記録の付与を理由に失敗する反映が 0 件) は、**内容を固定したことで
入力に依存しなくなっている。** 28 オクテットは宣言された上限 80 に収まり、
一度受け入れられれば以後も受け入れられる。確かめるべきは「その 1 つの値が
通るか」だけである。
