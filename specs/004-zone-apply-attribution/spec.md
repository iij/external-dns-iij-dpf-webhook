# Feature Specification: ゾーン反映の実行者を DPF の記録に残す

**Feature Branch**: `feature/create-webook`

**Created**: 2026-09-15

**Status**: Draft

**Input**: User description: "ゾーン反映時に、descriptionにexternal-dns-iij-dpf-webhookが実行したと言うのを記録してください。"

## User Scenarios & Testing *(mandatory)*

本機能の利用者は **DPF のゾーンを運用する人** である。本 provider が管理するゾーンを、
DPF コンソールから閲覧したり、自分で編集したりする。本 provider はそのゾーンを無人で
書き換えるため、**両者の変更が同じ履歴に混ざる。**

### User Story 1 - 履歴から変更の出どころを見分ける (Priority: P1)

ゾーンの運用者が DPF の履歴を開くと、そのゾーンに加えられた変更が時系列で並ぶ。
現状、本 provider による反映と人手による反映が同じ見た目で並び、どれが自動で、
どれが人の操作なのか分からない。本機能により、本 provider が行った反映には
その旨が記録され、一目で区別できるようになる。

**Why this priority**: これが本機能の価値のすべてである。他に成立させるべき
ストーリーはない。

**Independent Test**: 検証用ゾーンに対して本 provider から変更を適用し、DPF の
履歴を開く。当該の反映に、本 provider が実行したことを示す記録が付いていることを
確認する。続いて DPF コンソールから人手で変更を行い、両者が区別できることを
確認する。

**Acceptance Scenarios**:

1. **Given** 本 provider が管理するゾーンがある、**When** 本 provider が変更を
   適用する、**Then** その反映の記録に `external-dns-iij-dpf-webhook` が含まれる
2. **Given** 同じゾーンを人手で編集して反映した、**When** 運用者が履歴を見る、
   **Then** 人手による反映には本 provider の記録が付いておらず、両者を区別できる
3. **Given** 1 つの変更セットが複数のゾーンにまたがる、**When** 適用する、
   **Then** 反映したすべてのゾーンの記録に本 provider の記録が付く
4. **Given** 本 provider が連続して複数回の反映を行った、**When** 履歴を見る、
   **Then** そのすべてに記録が付いており、記録の付かない反映がない
5. **Given** 認証情報が設定されている、**When** 記録を参照する、**Then**
   認証情報の値は含まれない

---

### Edge Cases

- 空の変更セットが要求された場合、反映そのものが行われないため、記録も残らない
- 本 provider は、自身が行う反映にのみ記録を付ける。**過去の反映の記録や、
  他者が付けた記録を書き換えない**
- 記録の付与は DNS レコードの内容を変えない。同一の変更セットを再適用しても、
  DNS の最終状態は変わらない
- 記録の長さは DPF の上限 (80 オクテット) に収まる。識別名は 28 オクテットであり、
  入力によって変動しない
- 本機能より前に本 provider が行った反映は、履歴上で記録が空である。
  これを遡って埋めることはしない
- 適用が失敗した場合、記録だけが残ることはない。記録は反映と同じ操作の一部である
- レコード単位のコメントは本機能の対象外である。既存のコメントは従来どおり
  逐語的に保たれる

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、ゾーンの反映を行うたびに、実行者が本 provider である
  ことを示す記録を DPF に残さなければならない
- **FR-002**: 記録には、本 provider を識別する名前として
  `external-dns-iij-dpf-webhook` を含めなければならない
- **FR-003**: システムは、反映を行ったすべてのゾーンに記録を残さなければならない。
  変更セットが複数のゾーンにまたがる場合も、記録の付かないゾーンがあってはならない
- **FR-004**: システムは、記録に認証情報を含めてはならない
- **FR-005**: システムは、記録の付与によって DNS レコードの内容を変えてはならない。
  記録は反映操作に付随するものであり、ゾーンのレコードデータではない
- **FR-006**: システムは、記録を **80 オクテット以内**に収めなければならない。
  これは DPF がコメントに許す長さの上限である。上限を超える内容を記録しようと
  してはならず、収める過程で本 provider を識別する名前 (FR-002) が失われては
  ならない
- **FR-007**: システムは、レコード単位のコメントを本機能のために書き換えては
  ならない。既存のコメントは従来どおり保たれなければならない
- **FR-008**: システムは、過去の反映に付けられた記録、および他者が付けた記録を
  書き換えてはならない

### Key Entities

- **反映の記録**: ゾーンの反映操作に添える短い説明。DPF の履歴に残り、ゾーンの
  運用者が閲覧できる。DNS レコードの内容とは別のものであり、名前解決には影響しない

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: DPF の履歴を見た運用者が、本 provider による反映と人手による反映を
  100% 見分けられる
- **SC-002**: 本 provider が行った反映のうち、記録が付かないものが 0 件である
- **SC-003**: 記録に認証情報が 1 件も出現しない
- **SC-004**: 記録の付与の前後で、同一の変更セットを適用したときの DNS の最終状態が
  変わらない
- **SC-005**: 記録の付与を理由に失敗する反映が 0 件である

## Assumptions

- DPF はゾーンの反映操作に説明を添えられ、それを履歴として保持する。運用者は
  DPF コンソールまたは API からこれを閲覧できる
- 記録する内容は**本 provider の識別名に限る**。版番号、変更件数、対象レコード名
  などを含めることは本機能の範囲外とする。必要になった場合は別途 spec の改訂で
  追加する
- 同一ゾーンを複数の本 provider インスタンスが操作する構成は想定しない。
  したがって、記録によってインスタンスを区別する必要はない
- 記録は運用者が読むためのものであり、本 provider がこれを読み返して動作を
  変えることはない
- 本機能は 001 の適用経路に乗る。反映そのものの振る舞い (ロック、原子性、
  反映完了までの待ち合わせ) は変更しない

## Dependencies

- **001 の適用経路**: 記録は反映と同じ操作に添えられる。001 が確立した
  「ゾーンロック → マージ → 一括更新と反映 → 完了待ち」の流れに変更を加えない
- **DPF のゾーン履歴**: 記録の保存先。DPF が履歴を保持し閲覧できることが前提となる
- **検証用の DPF ゾーン**: 受け入れ確認には、履歴を確認できる検証用ゾーンが必要である

## 背景: なぜ必要か

001 の利用前提条件 (PC-001〜PC-004) は、本 provider が管理するゾーンを他者と
共有する場合の制約を定めている。**本 provider の変更は、他の変更者から見て
区別がつかない。** 誰が何をしたか分からないまま、互いの変更を取り消し合う
可能性がある構成を運用することになる。

記録を残しても競合そのものは防げない。防げないが、**起きたことを後から追える**
ようにはなる。「このレコードはいつ誰が変えたのか」という問いに、DPF の履歴だけで
答えられる状態にすることが本機能の目的である。
